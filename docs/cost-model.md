## 1. 前提 — なぜルーティングがコスト設計になるのか

本製品は 1 セッションで LLM を **10〜15 回**呼ぶ。
すべてを同じモデルで処理すると、**回数の多い処理が単価の高いモデルを引きずる**。

一方で、本製品の LLM 呼び出しには**性質のはっきりした偏り**がある。

| 性質 | 該当する処理 | 回数 |
|---|---|---|
| **推論精度が要る。難しい。** | 原因の特定（Diagnoser） | **1 回だけ** |
| **速度と制約遵守が要る。難しくない。** | ヒント生成・出題・判定 | **10〜15 回** |

**難しい処理が 1 回しかなく、簡単な処理が大半を占める。**
この偏りがあるからこそ、モデルを出し分けるだけでコストが大きく下がる。

> OrcaRouter が OpenAI 互換のゲートウェイであるため、
> **`model` パラメータを変えるだけでプロバイダをまたいだ出し分けができる**。
> クライアントは 1 つのままでよく、実装コストはほぼゼロ。

## 2. 役割別のモデル割り当て

| 役割 | 何をするか | 求められる性質 | モデル階層 | 環境変数 | 回数 / セッション |
|---|---|---|---|---|---|
| **Diagnoser** | エラーから原因・根拠・着眼点を特定する | **推論精度** | **高品質** | `MODEL_DIAGNOSER` | 1 |
| Hinter | 着眼点から Gate A のヒントを作る | 制約遵守・速度 | 安価 | `MODEL_QUESTIONER` | 1 |
| Questioner | 着眼点から選択式の設問を作る | 制約遵守・速度 | 安価 | `MODEL_QUESTIONER` | 8〜12 |
| Judge | 原因宣言の到達判定 | 短文生成・速度 | 安価 | `MODEL_JUDGE` | 1〜3 |
| Revealer | Gate C の解説を作る | 文章品質 | 高品質 | `MODEL_DIAGNOSER` | 0〜1 |
| Reporter | 振り返りと一般化された学びを作る | 文章品質 | 高品質 | `MODEL_DIAGNOSER` | 1 |

### 設計の核心

**Diagnoser の出力を使い回す。**
1 回の高品質な診断で得た `focusHints` を、以降 10 回以上の安価な出題がすべて参照する。

```
  Diagnoser（高品質・1 回）
      │  focusHints（着眼点だけ。結論は渡さない）
      ├──────▶ Hinter      （安価）
      ├──────▶ Questioner  （安価）× 8〜12
      └──────▶ Questioner  （安価）
```

**再診断しない**（NFR-C3）。診断結果は `session_secrets` に保存し、
セッション中は読み出すだけにする。

> これは**コスト削減のための妥協ではなく、品質のための設計**でもある。
> 毎回診断し直すと、セッション中に原因の見立てがブレて問いの一貫性が壊れる。
> **コスト設計と品質設計がここで一致している。**

## 3. max_tokens の設定（F04）

役割ごとに出力の上限を設ける。
**上限は「必要な長さ」から決める。多めに取らない。**

| 役割 | `max_tokens` | 根拠 |
|---|---|---|
| Diagnoser | **1600** | 構造化 JSON。`focusHints` 5 件 + 根拠 + 誤答素材 + **Gate A のヒント 3 件** |
| Hinter | **300** | ヒントは 1〜2 文 |
| Questioner | **900** | 質問文 1 文 + 選択肢 5 つ + 誤答ごとの誘導文 4 つ |
| Judge | **500** | 判定 + フィードバック 1〜2 文 |
| Revealer | **1000** | 原因・根拠・修正方針・再発防止の 4 項目 |
| Reporter | **1000** | 振り返り + 一般化された学び + 次回の 3 ステップ |

> **上表は実測で引き上げた値である。** 当初の見積もり（Diagnoser 800 / Questioner 500 …）は
> 英語の出力密度を前提にしており、**日本語では収まらなかった。**
> 実際に `MAX_TOKENS_DIAGNOSER=800` で本番モデルを呼ぶと、
> 高品質モデルと退避モデルの**両方が `max_tokens reached` で失敗**し、
> 診断なしの汎用モードに落ちた。
>
> **上限を上げてもコストは増えない。** これは上限であって使用量ではなく、
> 課金は実際に生成された長さで決まる。逆に**足りないと全額が無駄になる**
> （切れた JSON は使えないのに、そこまでのトークンは課金される）。
> したがって「必要な長さ」より少し余裕を持たせる方が安い。
>
> Diagnoser だけ突出しているのは、**Gate A のヒント 3 件を同じ呼び出しで返す**設計のため
> （追加の LLM 呼び出しを発生させない / NFR-C5・socratic-engine.md §6）。

**上限に達した場合は生成失敗として扱う**（途中で切れた JSON を無理に使わない）。
フォールバックモデルで 1 回だけ再試行し、それも失敗したら定型テンプレートに落とす。

### セッション単位の上限（NFR-C1）

```
SESSION_TOKEN_BUDGET=80000   # 入出力合計
```

超過時は `429 TOKEN_BUDGET_EXCEEDED` を返し、セッションを打ち切る。
**1 人のユーザーが無制限に課金を発生させられない状態にする。**

## 4. 単価ログの出力（F11）

### 4.1 出力するもの

**すべての LLM 呼び出しについて、1 リクエスト単位で記録する。**

```jsonc
{
  "type": "llm_call",
  "sessionId": "01J8XK4M2N0000000000000001",
  "role": "questioner",
  "model": "openai/gpt-4o-mini",
  "tier": "cheap",                    // cheap | quality
  "promptTokens": 1842,
  "completionTokens": 312,
  "latencyMs": 1240,
  "estimatedCostUsd": 0.000464,
  "estimatedCostJpy": 0.070,
  "orcaHeaders": { "x-orca-provider": "openai" },
  "leakGuardHit": false,
  "ts": 1786000012345
}
```

セッション完了時にはサマリも出す。

```jsonc
{
  "type": "session_cost",
  "sessionId": "01J8XK4M2N0000000000000001",
  "reachedGate": "B",
  "calls": { "quality": 2, "cheap": 12 },
  "tokens": { "prompt": 28400, "completion": 5100 },
  "costUsd": 0.0212,
  "costJpy": 3.2,
  "breakdown": { "diagnoser": 0.0148, "questioner": 0.0051, "judge": 0.0008, "reporter": 0.0005 }
}
```

### 4.2 単価の持ち方

モデルごとの単価を設定として持ち、トークン数から算出する。

```ts
// packages/llm/src/pricing.ts
// 単価は USD / 1M tokens。OrcaRouter のカタログを見て設定する（未決 Q-1）
export const PRICING: Record<string, { input: number; output: number; tier: 'cheap' | 'quality' }> = {
  'openai/gpt-4o-mini':          { input: 0.15, output: 0.60, tier: 'cheap'   },
  'google/gemini-2.5-flash':     { input: 0.30, output: 2.50, tier: 'cheap'   },
  'anthropic/claude-sonnet-4.6': { input: 3.00, output: 15.00, tier: 'quality' },
}

export function estimateCost(model: string, promptTokens: number, completionTokens: number) {
  const p = PRICING[model]
  if (!p) return null            // 未知のモデルは null。0 と混同しない
  return (promptTokens * p.input + completionTokens * p.output) / 1_000_000
}
```

> **単価表はコードに持ち、モデル ID をキーにする。**
> OrcaRouter がプロバイダをまたぐため、モデルを差し替えたら単価も自動で切り替わる。
> 未知のモデルには `null` を返し、**「単価不明」と「無料」を区別する**。

### 4.3 出力先

| 先 | 用途 |
|---|---|
| 実行環境の標準ログ（構造化 JSON） | 常時。運用時の監視 |
| `ops_logs` テーブル | v0.1 では**有効**。実測コスト表の集計に使う（[scope-v0.1.md §4.4](scope-v0.1.md#44-データストアのテーブルを-5-つに絞る)） |

**PII は記録しない。** エラーテキストの本文はログに出さず、
トークン数と役割だけを記録する（[security.md](security.md)）。

## 5. コスト表

> ### ✅ 請求と突き合わせ済み（2026-08-12）
>
> 本節の金額は、トークン数の実測に
> [pricing.ts](../packages/llm/src/pricing.ts) の単価表を掛けた値である。
> レビューで「単価表は OrcaRouter の課金と突き合わせていないのでは」との
> 指摘を受け、**実際にクレジット消費と突き合わせた。**
>
> #### 実測できたのは 2 回目だけ
>
> | | 内部推定（ops_logs） | 請求（クレジット差分） |
> |---|---:|---:|
> | **2 回目・4 セッション / 26 回** | **0.1166 USD** | **0.11 USD** |
>
> **差は 6%。** ただしクレジット表示が 1 セント単位のため、
> 請求の真値は 0.105〜0.115 USD の幅がある。**差の範囲は 1〜11%。**
>
> #### 1 回目は補強材料（内部推定は無い）
>
> 1 回目の 4 セッションは `OPS_LOG_ENABLED` が false で**記録が残っていない**。
> 請求 **0.12 USD** だけが分かっている。同じスクリプト・同じ構成なので、
> **2 回とも推定 0.1166 USD の ±10% に収まっている**ことが確認できる。
>
> **結論: 単価表は妥当。** ただし主張できる精度は 6%（分解能を含めると最大 11%）であり、
> より細かい検証には**セッション数を増やして分解能の影響を薄める**必要がある。
>
> 集計は [scripts/cost-report.mjs](../scripts/cost-report.mjs) で再現できる。
>
> #### レビューで指摘された「1 セッション $0.0205」について
>
> **MOCK モードのセッションを含めて割った値だった。**
>
> | | 件数 |
> |---|---:|
> | セッション作成 | 20 |
> | うち実 LLM | 13 |
> | うち MOCK のみ（課金ゼロ） | 3 |
> | うち記録なし | 4 |
>
> 実 LLM の 13 件で割ると **$0.0288**。今回の計測（$0.02915 / セッション）とも
> 一致する。**単価表のずれではなかった。**
>
> #### 計測時の注意
>
> - **クレジット表示には反映の遅れがある。** 直後に読むと少なく見え、
>   実際に $0.08 → $0.11 と変わった。少し待ってから読むこと
> - **`OPS_LOG_ENABLED` が false だと記録が残らない。** 課金はされるのに
>   `GET /cost` は呼び出し 0 件を返し、MOCK と見分けがつかない。
>   `GET /v1/health` の `limits.opsLog` で事前に確認すること
> - **計測は 1 アカウントに統一する。** 使い捨てアカウントで回すと後から集計できない
>
> #### 未検証のモデル
>
> 突き合わせたのは実際に使っている 2 モデル
> （`claude-sonnet-4.6` / `gpt-4o-mini`）だけである。
> **使うモデルを変えたら突き合わせ直すこと。**
>
> ### 換算レート
>
> **本節は USD を主とし、円は 1 USD = 165 円で換算する。**
> 実行環境の `USD_JPY_RATE` と一致させている。効いている値は
> `GET /v1/health` の `limits.usdJpyRate` で確認できる。
>
> 以前は 150 換算と 165 換算が混在していた（実行環境が 165、コードの既定と
> 本書の一部が 150）。**その結果「試算とほぼ一致（±5%）」という誤った結論を
> 書いていた** — 150 換算の試算と 165 換算の実測を比べていたためである。

### 5.1 1 セッションの内訳（試算 / Gate B で解決するケース）

| 役割 | モデル階層 | 回数 | 入力 tok | 出力 tok | 小計 (USD) |
|---|---|---:|---:|---:|---:|
| Diagnoser | 高品質 | 1 | 3,000 | 800 | 0.0210 |
| Hinter | 安価 | 1 | 1,200 | 150 | 0.0003 |
| Questioner | 安価 | 10 | 18,000 | 3,500 | 0.0048 |
| Judge | 安価 | 2 | 3,000 | 300 | 0.0007 |
| Reporter | 高品質 | 1 | 2,500 | 600 | 0.0165 |
| **合計** | | **15** | **27,700** | **5,350** | **0.0433** |

**0.0433 USD / セッション**（1 USD = 165 円で **約 7.1 円**）

> **この表は Gate B で解決するケースなので、Revealer（Gate C の解説）を含んでいない。**
> Gate C まで到達すると Revealer が 1 回加わり、**実測ではセッションコストの 29% を占める**
> （§5.4）。**§2 の想定表には「Revealer 0〜1 回」とあるのに、この内訳表から抜けていた。**
> 到達ゲートによって原価が変わることが、この表からは読み取れなかった。

### 5.2 出し分けの効果

| 構成 | 1 セッション（試算） | 1 セッション（**推定 / トークンは実測**） |
|---|---:|---:|
| すべて高品質モデル | 0.1637 USD（約 27.0 円） | 0.0759 USD（約 12.5 円） |
| **役割別に出し分け（採用案）** | 0.0433 USD（約 7.1 円） | **0.0414 USD（約 6.8 円）** |
| 削減率 | **74%** | **45%** |

> **実測の削減率は 74% ではなく 45% だった。** 試算が Questioner を
> 入力 18,000 tok と見込んでいたのに対し、実測は 4,943 tok だったため。
> **安くする対象が小さければ、節約額も小さくなる。**
>
> ただしこれは**設問がいちばん少ないケース**（5 問すべて 1 問目で正解）の数字である。
> 詰まって同段階で 3 問ずつ出題される場合（最大 15 問）は **68%** まで上がる。
>
> **削減率は「利用者が設問を何問解いたか」に依存する。** 単一の数字で語れない。

すべて安価にすればさらに安いが、**Diagnoser の推論精度が落ちると
着眼点が的外れになり、以降の設問がすべて無意味になる**。

> **一番効くのは「安くする」ことではなく「安くしてよい場所を見極める」こと。**
> Diagnoser は 1 回しか呼ばれないので、ここに高いモデルを使っても
> セッション全体では 2 回分にしかならない。
> 逆に Questioner は 10 回以上呼ばれるので、ここを安価にすると効果が 10 倍で効く。
> **回数 × 単価で考えると、投資すべき場所と削るべき場所が自動的に決まる。**

### 5.3 規模別の月額

実測トークン × 推定単価の平均 **0.0361 USD（約 6.0 円）/ セッション**で再計算した（括弧内は試算時の値。いずれも 1 USD = 165 円）。

| 利用規模 | セッション / 月 | 月額 |
|---|---:|---:|
| 個人（週 2 回） | 8 | 約 **48** 円（57 円） |
| 小チーム 10 名（週 2 回） | 80 | 約 **480** 円（570 円） |
| 100 名（週 2 回） | 800 | 約 **4,800** 円（5,700 円） |

**1 人あたり月 48 円。** 業務支援ツールとして成立する水準である。
（金額は請求と突き合わせ済み。差 6% → 本節冒頭）

### 5.4 実測結果

| 項目 | 値 |
|---|---|
| 計測日 | 2026-08-11 |
| 使用モデル（高品質） | `anthropic/claude-sonnet-4.6`（Diagnoser / Revealer / Reporter） |
| 使用モデル（安価） | `openai/gpt-4o-mini`（Hinter / Questioner / Judge） |
| 退避先 | `google/gemini-2.5-flash` |
| 計測セッション数 | 3（Gate A 到達 1 / Gate C 到達 2） |
| 平均コスト / セッション | **0.0361 USD**（0.0295〜0.0414 / 約 6.0 円） |
| 試算との差 | 試算 0.0433 USD に対し **17% 安い** |
| ★ 請求との突き合わせ | **済**（差 6% / 分解能込み 1〜11% → 本節冒頭） |

> **「ほぼ一致（±5%）」は誤りだった。** 150 換算の試算（6.5 円）と
> 165 換算の推定（5.9 円）を比べていたためである。USD で比べると
> **試算 0.0433 に対し 0.0361 で 17% 安い**。試算の精度としては妥当な範囲だが、
> 「ほぼ一致」と言える差ではない。**単位を揃えずに比べると結論が変わる。**

**Gate A で自力到達した場合（4 回・0.0295 USD / 約 4.9 円）**

| 役割 | モデル | 入力 tok | 出力 tok | 所要 |

| Hinter | 安価 | 363 | 24 | 1.1s |

| Judge | 安価 | 818 | 74 | 1.3s |
| Reporter | 高品質 | 1,015 | 437 | 11.8s |

**Gate C まで到達した場合（既定の 5 段階・10 回・0.0414 USD / 約 6.8 円）**

| 役割 | モデル | 回数 | 入力 tok | 出力 tok |
|---|---|---:|---:|---:|
| Hinter | 安価 | 1 | 363 | 24 |

段階数を 3 に絞った運用では 6.19 円。**5 段階との差は 0.64 円**で、
Questioner が安価モデルであることの効果がそのまま出ている
（出し分けをしなければ、この 2 回分だけで 1 円を超える）。

### 5.5 実測から分かったこと

| # | 分かったこと |
|---|---|
| 1 | **`max_tokens` の当初見積もりが小さすぎた。** 日本語では Diagnoser が 800 に収まらず、高品質・退避の両モデルが失敗して診断なしの汎用モードに落ちた。実測の最大出力は 1,075 tok（→ §3 を改訂） |
| 2 | **上限に達した生成も課金される。** 切れた JSON は使えないのに、そこまでのトークンは請求される。失敗 1 回あたり約 2.6 円が無駄になっていた |
| 3 | **モデル出し分けは効いているが、内訳は試算と違った。** コストの **96% を高品質モデルの 3 役割**（Diagnoser / Revealer / Reporter）が占め、安価モデルの 3 役割は合計 3.9%。§5.1 の試算表には **Revealer が抜けていた**（実測では 29%） |
| 4 | Diagnoser のレイテンシが約 21 秒。**別リクエストへの分離（ADR-006）がなければ NFR-P1（5 秒以内）は成立しない**。実測でセッション作成は 1.4〜1.6 秒 |
| 5 | **設問はもう最適化の対象ではない。** 出し分けが効きすぎて、Questioner はセッションコストの 3.4%（設問 1 問 0.043 円）まで下がった。次に削るなら高品質モデルの 3 役割（96%）である |

### 5.6 役割別の実測出力トークン（`max_tokens` の根拠）

| 役割 | 実測の最大出力 | 設定値 | 余裕 |
|---|---:|---:|---|
| Diagnoser | 1,075 | 1,600 | 1.5 倍 |
| Revealer | 578 | 1,000 | 1.7 倍 |
| Reporter | 494 | 1,000 | 2.0 倍 |
| Questioner | 264 | 900 | 3.4 倍 |
| Judge | 74 | 500 | 6.8 倍 |
| Hinter | 24 | 300 | 12.5 倍 |

> **余裕を持たせても課金は増えない**（上限であって使用量ではない）。
> 逆に足りないと全額が無駄になるため、**実測の 1.5 倍以上**を保つ方針とする。

### 5.7 原価は「使った量」ではなく「開始した回数」で決まる

実測して分かった、価格設計に直結する構造。

| | 内容 |
|---|---|
| **固定費** | Diagnoser + Reporter は**どのセッションでも必ず 1 回ずつ**呼ばれる。**セッションを開始した時点で約 4.2 円が確定する** |
| 変動費 | 設問は 1 問 0.043 円。**100 問解いても 4.3 円**しか増えない |
| 分岐 | Gate C まで到達すると Revealer が加わり **+1.8 円** |

実測でも、Gate A で即解決（0.0295 USD / 約 4.9 円）と
Gate C まで到達（0.0414 USD / 約 6.8 円）の差は **0.012 USD（約 2 円）**しかない。
**利用者がどれだけ考えても原価はほとんど動かず、セッションを何回開始したかで決まる。**

#### この構造が、守るべき非機能要件を決める

| 要件 | 実測での効き方 |
|---|---|
| **NFR-O3**（10 セッション / 時 / メンバー） | ✅ **これが価格を守っている。** 原価はセッション数に比例するため |
| NFR-C1（1 セッション 80,000 tokens 上限） | ⚠️ **価格の防波堤としては機能していない** |

実測のトークン消費は **12,626 tok** で、上限 80,000 の **16%** にすぎない。
しかも上限に近づく経路は Questioner（安価）の繰り返しなので、
**80,000 tok まで使い切っても 1 セッション 8.6 円程度**にしかならない。

> **「非機能要件がそのまま価格を守る設計になっている」と説明するなら、NFR-O3 に絞るのが正確。**
> NFR-C1 は暴走（無限ループ的な生成）に対する保険としては有効だが、
> **コスト上限としてはほとんど効いていない。**
>
> **論点**: `SESSION_TOKEN_BUDGET` の既定 80,000 は、実測の 6 倍以上に相当する。
> 上限としての意味を持たせるなら 30,000 前後まで下げる余地がある。
> ただし詰まって設問を重ねた利用者を打ち切ることになるため、
> **P2（業務支援を最優先）との兼ね合いで判断する。**（→ requirements.md NFR-C1）

## 6. さらに削減できる余地（v0.1 ではやらない）

| 案 | 効果 | 見送る理由 |
|---|---|---|
| プロンプトキャッシュ | Diagnoser の入力を再利用する場面で有効 | 本製品は診断が 1 回だけなので、キャッシュが効く場面が少ない |
| 設問のテンプレート化 | Questioner の呼び出しを減らせる | 問いの個別化が価値の中核。ここを削ると製品ではなくなる |
| 演習モードで Diagnoser を省略 | 演習セッションで最も高い呼び出しが消える | 演習モードは v0.2（F16 相当）。実装時に必ず入れる |
| 出力の短縮（max_tokens を下げる） | 出力側の単価は入力の 4〜5 倍のため効果が大きい | 既に必要最小限で設定済み（§3） |

> **演習モードでの Diagnoser 省略は、v0.2 で最も効く削減策。**
> 問題集に診断が事前保存されるため、高品質モデルの呼び出しが
> セッションあたり 2 回 → 1 回（Reporter のみ）になる。
> コストが約半分になり、かつ**全員が同一の診断で出題される**ため評価の条件も揃う。
> コスト削減と評価妥当性が同じ設計で両立する。

## 7. MOCK モードとコスト（F04）

`MOCK_MODE=true` のとき、LLM を一切呼ばない。

| 効く場面 | コストへの効果 |
|---|---|
| UI 開発 | 開発中の課金がゼロ |
| 自動テスト | CI で LLM を呼ばない |
| デモのリハーサル | 何度リハーサルしても課金されない |

**開発期間中のコストの大半は「試行錯誤」で発生する。**
MOCK モードはその大半を消す。コスト設計の一部として最初に実装する。
