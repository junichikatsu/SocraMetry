## 1. 前提 — なぜルーティングがコスト設計になるのか

本製品は 1 セッションで LLM を **10〜15 回**呼ぶ。
すべてを同じモデルで処理すると、**回数の多い処理が単価の高いモデルを引きずる**。

一方で、本製品の LLM 呼び出しには**性質のはっきりした偏り**がある。

| 性質 | 該当する処理 | 回数 |
|---|---|---|
| **推論精度が要る。難しい。** | 原因の特定（Diagnoser） | **1 回だけ** |
| **速度と制約遵守が要る。難しくない。** | ヒント生成・出題・判定 | **10〜15 回** |

**難しい処理が 1 回しかなく、簡単な処理が大半を占める。**
この偏りがあるからこそ、モデルを出し分けるだけでコストが大きく下がる。

> OrcaRouter が OpenAI 互換のゲートウェイであるため、
> **`model` パラメータを変えるだけでプロバイダをまたいだ出し分けができる**。
> クライアントは 1 つのままでよく、実装コストはほぼゼロ。

## 2. 役割別のモデル割り当て

| 役割 | 何をするか | 求められる性質 | モデル階層 | 環境変数 | 回数 / セッション |
|---|---|---|---|---|---|
| **Diagnoser** | エラーから原因・根拠・着眼点を特定する | **推論精度** | **高品質** | `MODEL_DIAGNOSER` | 1 |
| Hinter | 着眼点から Gate A のヒントを作る | 制約遵守・速度 | 安価 | `MODEL_QUESTIONER` | 1 |
| Questioner | 着眼点から選択式の設問を作る | 制約遵守・速度 | 安価 | `MODEL_QUESTIONER` | 8〜12 |
| Judge | 原因宣言の到達判定 | 短文生成・速度 | 安価 | `MODEL_JUDGE` | 1〜3 |
| Revealer | Gate C の解説を作る | 文章品質 | 高品質 | `MODEL_DIAGNOSER` | 0〜1 |
| Reporter | 振り返りと一般化された学びを作る | 文章品質 | 高品質 | `MODEL_DIAGNOSER` | 1 |

### 設計の核心

**Diagnoser の出力を使い回す。**
1 回の高品質な診断で得た `focusHints` を、以降 10 回以上の安価な出題がすべて参照する。

```
  Diagnoser（高品質・1 回）
      │  focusHints（着眼点だけ。結論は渡さない）
      ├──────▶ Hinter      （安価）
      ├──────▶ Questioner  （安価）× 8〜12
      └──────▶ Questioner  （安価）
```

**再診断しない**（NFR-C3）。診断結果は `session_secrets` に保存し、
セッション中は読み出すだけにする。

> これは**コスト削減のための妥協ではなく、品質のための設計**でもある。
> 毎回診断し直すと、セッション中に原因の見立てがブレて問いの一貫性が壊れる。
> **コスト設計と品質設計がここで一致している。**

## 3. max_tokens の設定（F04）

役割ごとに出力の上限を設ける。
**上限は「必要な長さ」から決める。多めに取らない。**

| 役割 | `max_tokens` | 根拠 |
|---|---|---|
| Diagnoser | 800 | 構造化 JSON。`focusHints` 5 件 + 根拠で足りる |
| Hinter | 200 | ヒントは 1〜2 文 |
| Questioner | 500 | 質問文 1 文 + 選択肢 4 つ + 誘導文 |
| Judge | 300 | 判定 + フィードバック 1〜2 文 |
| Revealer | 600 | 原因・根拠・修正方針・再発防止の 4 項目 |
| Reporter | 800 | 振り返り + 一般化された学び + 次回の 3 ステップ |

**上限に達した場合は生成失敗として扱う**（途中で切れた JSON を無理に使わない）。
フォールバックモデルで 1 回だけ再試行し、それも失敗したら定型テンプレートに落とす。

### セッション単位の上限（NFR-C1）

```
SESSION_TOKEN_BUDGET=80000   # 入出力合計
```

超過時は `429 TOKEN_BUDGET_EXCEEDED` を返し、セッションを打ち切る。
**1 人のユーザーが無制限に課金を発生させられない状態にする。**

## 4. 単価ログの出力（F11）

### 4.1 出力するもの

**すべての LLM 呼び出しについて、1 リクエスト単位で記録する。**

```jsonc
{
  "type": "llm_call",
  "sessionId": "01J8XK4M2N0000000000000001",
  "role": "questioner",
  "model": "openai/gpt-4o-mini",
  "tier": "cheap",                    // cheap | quality
  "promptTokens": 1842,
  "completionTokens": 312,
  "latencyMs": 1240,
  "estimatedCostUsd": 0.000464,
  "estimatedCostJpy": 0.070,
  "orcaHeaders": { "x-orca-provider": "openai" },
  "leakGuardHit": false,
  "ts": 1786000012345
}
```

セッション完了時にはサマリも出す。

```jsonc
{
  "type": "session_cost",
  "sessionId": "01J8XK4M2N0000000000000001",
  "reachedGate": "B",
  "calls": { "quality": 2, "cheap": 12 },
  "tokens": { "prompt": 28400, "completion": 5100 },
  "costUsd": 0.0212,
  "costJpy": 3.2,
  "breakdown": { "diagnoser": 0.0148, "questioner": 0.0051, "judge": 0.0008, "reporter": 0.0005 }
}
```

### 4.2 単価の持ち方

モデルごとの単価を設定として持ち、トークン数から算出する。

```ts
// packages/llm/src/pricing.ts
// 単価は USD / 1M tokens。OrcaRouter のカタログを見て設定する（未決 Q-1）
export const PRICING: Record<string, { input: number; output: number; tier: 'cheap' | 'quality' }> = {
  'openai/gpt-4o-mini':          { input: 0.15, output: 0.60, tier: 'cheap'   },
  'google/gemini-2.5-flash':     { input: 0.30, output: 2.50, tier: 'cheap'   },
  'anthropic/claude-sonnet-4.6': { input: 3.00, output: 15.00, tier: 'quality' },
}

export function estimateCost(model: string, promptTokens: number, completionTokens: number) {
  const p = PRICING[model]
  if (!p) return null            // 未知のモデルは null。0 と混同しない
  return (promptTokens * p.input + completionTokens * p.output) / 1_000_000
}
```

> **単価表はコードに持ち、モデル ID をキーにする。**
> OrcaRouter がプロバイダをまたぐため、モデルを差し替えたら単価も自動で切り替わる。
> 未知のモデルには `null` を返し、**「単価不明」と「無料」を区別する**。

### 4.3 出力先

| 先 | 用途 |
|---|---|
| 実行環境の標準ログ（構造化 JSON） | 常時。運用時の監視 |
| `ops_logs` テーブル | v0.1 では**有効**。実測コスト表の集計に使う（[scope-v0.1.md §4.4](scope-v0.1.md#44-データストアのテーブルを-5-つに絞る)） |

**PII は記録しない。** エラーテキストの本文はログに出さず、
トークン数と役割だけを記録する（[security.md](security.md)）。

## 5. 実測コスト表

> **以下は設計時の試算。** 実際の単価は OrcaRouter のカタログ（`GET /v1/models`）で確定し（未決 Q-1）、
> 実測値は開発完了後に本表を更新する。**試算と実測を混ぜない。**

### 5.1 1 セッションの内訳（試算 / Gate B で解決するケース）

| 役割 | モデル階層 | 回数 | 入力 tok | 出力 tok | 小計 (USD) |
|---|---|---:|---:|---:|---:|
| Diagnoser | 高品質 | 1 | 3,000 | 800 | 0.0210 |
| Hinter | 安価 | 1 | 1,200 | 150 | 0.0003 |
| Questioner | 安価 | 10 | 18,000 | 3,500 | 0.0048 |
| Judge | 安価 | 2 | 3,000 | 300 | 0.0007 |
| Reporter | 高品質 | 1 | 2,500 | 600 | 0.0165 |
| **合計** | | **15** | **27,700** | **5,350** | **0.0433** |

**約 6.5 円 / セッション**（1 USD = 150 円で換算）

### 5.2 出し分けの効果

| 構成 | 1 セッションのコスト（試算） | 比 |
|---|---:|---:|
| **すべて高品質モデル** | 0.1637 USD（約 24.6 円） | 100% |
| **役割別に出し分け（採用案）** | 0.0433 USD（約 6.5 円） | **26%** |
| すべて安価モデル | 0.0075 USD（約 1.1 円） | 5% |

**出し分けにより約 74% の削減。**
すべて安価にすればさらに安いが、**Diagnoser の推論精度が落ちると
着眼点が的外れになり、以降 10 回以上の設問がすべて無意味になる**。

> **一番効くのは「安くする」ことではなく「安くしてよい場所を見極める」こと。**
> Diagnoser は 1 回しか呼ばれないので、ここに高いモデルを使っても
> セッション全体では 2 回分にしかならない。
> 逆に Questioner は 10 回以上呼ばれるので、ここを安価にすると効果が 10 倍で効く。
> **回数 × 単価で考えると、投資すべき場所と削るべき場所が自動的に決まる。**

### 5.3 規模別の月額（試算）

| 利用規模 | セッション / 月 | 月額（試算） |
|---|---:|---:|
| 個人（週 2 回） | 8 | 約 52 円 |
| 小チーム 10 名（週 2 回） | 80 | 約 520 円 |
| 100 名（週 2 回） | 800 | 約 5,200 円 |

**1 人あたり月 50 円程度。** 業務支援ツールとして十分に成立する水準。

## 6. さらに削減できる余地（v0.1 ではやらない）

| 案 | 効果 | 見送る理由 |
|---|---|---|
| プロンプトキャッシュ | Diagnoser の入力を再利用する場面で有効 | 本製品は診断が 1 回だけなので、キャッシュが効く場面が少ない |
| 設問のテンプレート化 | Questioner の呼び出しを減らせる | 問いの個別化が価値の中核。ここを削ると製品ではなくなる |
| 演習モードで Diagnoser を省略 | 演習セッションで最も高い呼び出しが消える | 演習モードは v0.2（F16 相当）。実装時に必ず入れる |
| 出力の短縮（max_tokens を下げる） | 出力側の単価は入力の 4〜5 倍のため効果が大きい | 既に必要最小限で設定済み（§3） |

> **演習モードでの Diagnoser 省略は、v0.2 で最も効く削減策。**
> 問題集に診断が事前保存されるため、高品質モデルの呼び出しが
> セッションあたり 2 回 → 1 回（Reporter のみ）になる。
> コストが約半分になり、かつ**全員が同一の診断で出題される**ため評価の条件も揃う。
> コスト削減と評価妥当性が同じ設計で両立する。

## 7. MOCK モードとコスト（F04）

`MOCK_MODE=true` のとき、LLM を一切呼ばない。

| 効く場面 | コストへの効果 |
|---|---|
| UI 開発 | 開発中の課金がゼロ |
| 自動テスト | CI で LLM を呼ばない |
| デモのリハーサル | 何度リハーサルしても課金されない |

**開発期間中のコストの大半は「試行錯誤」で発生する。**
MOCK モードはその大半を消す。コスト設計の一部として最初に実装する。
