## M1: 技術検証（Spike）

**目的**: 製品が成立しなくなる 2 つのリスクを、UI を作る前に潰す。

### 1-A. 「答えを言わない」がプロンプトで実現できるか（最重要）

ここが崩れると製品価値がゼロになる。最初に確かめる。

- [ ] OrcaRouter 疎通（`GET /v1/models` でカタログ取得、用途別モデル ID を確定 → **Q-1**）
- [ ] Diagnoser の構造化出力（JSON Schema 準拠）を CLI で実行
- [ ] Questioner に `focusHints` だけを渡し、答えを漏らさず出題できるか検証
- [ ] LeakGuard の検出ルールを実装し、代表 20 ケースで検証
- [ ] 実際のエラー 10 件で、Lv1〜Lv5 を手動で通しでやってみる

**受け入れ条件**:
- 10 件中 8 件以上で、Lv1〜Lv5 のすべての生成文に答えの漏洩がない
- Diagnoser の原因特定が 10 件中 7 件以上で妥当

> **漏洩が止まらない場合**、Questioner に渡す情報をさらに削るか、
> 選択肢を LLM 生成ではなくテンプレート化する方向に設計を変更する。

### 1-B. enebular 上で設計どおりに動くか

ドキュメントから読み取れなかった仕様を、最小の ZIP を投げて実測で埋める。

- [ ] **エコー関数をデプロイし、HTTP トリガーが渡す `event` の形式を確認**（→ **Q-6**）
      API Gateway v1 / v2 / Function URL のどれか。`hono/aws-lambda` がそのまま使えるか
- [ ] `hono/aws-lambda` の `handle()` で Hono アプリが動くか（→ [ADR-009](architecture.md#adr-009-hono-を-lambda-ハンドラのルーターとして使う)）
- [ ] esbuild バンドル ZIP がそのまま動くか（ワークスペース依存を含めて）（→ [ADR-008](architecture.md#adr-008-esbuild-で単一-commonjs-ファイルにバンドルして-zip-化する)）
- [ ] **タイムアウトの上限値**と、20 秒級の LLM 呼び出しが完走するか（→ **Q-5**）
- [ ] `bulk-update cloud-config` の `envVars` で環境変数が読めるか（→ **Q-8**）
- [ ] `connectDataStore` 有効時に `@uhuru/enebular-sdk` が認証なしで動くか
- [ ] データストアの `query` で、メインキー一致 + サブキー範囲・降順（`order: false`）が期待どおり動くか
- [ ] ULID をサブキーにしたときの辞書順ソートが時系列順になるか
- [ ] コールドスタート時のレイテンシ実測（NFR-P1 の 5 秒に影響する）
- [ ] `enebular-cli` によるデプロイを GitHub Actions から 1 回通す

**受け入れ条件**:
- ZIP デプロイした Hono アプリが `GET /v1/health` を返す
- データストアへの put / get / query が動く
- GitHub Actions からのデプロイが成功する

> **1-B は 1-A と並行して進めてよい。** 1-A はローカルで完結し、1-B はデプロイ検証のため、
> 依存関係がない。

## M2: MVP（コア体験の一気通貫 + CD）

**目的**: 「エラーを投げる → 段階的に問われる → 自力で気づく」を通しで動かす。

### 基盤
- [ ] モノレポ初期化（pnpm workspaces + Turborepo）
- [ ] `packages/shared`: Zod スキーマ（API 契約）
- [ ] `packages/core`: 段階遷移ステートマシン / マスキング / LeakGuard / ULID（**単体テスト付き**）
- [ ] `packages/datastore`: 4 テーブルのリポジトリ層
- [ ] `packages/llm`: OrcaRouter クライアント + Diagnoser / Questioner / Judge

### バックエンド（apps/function）
- [ ] Hono アプリと Lambda アダプタ、ローカル起動（`local.ts`）
- [ ] `POST /sessions`（診断を待たない）, `POST /diagnose`（先行診断）
- [ ] `POST /answers`, `POST /hints`, `POST /conclusion`
- [ ] 匿名 ID Cookie ミドルウェアと CORS
- [ ] 冪等性の実装（FR-17）

### フロントエンド（apps/web）
- [ ] エラー投稿フォーム
- [ ] 問答画面（質問カード / 選択肢 / 段階プログレス / ヒントボタン）
- [ ] **「先輩が考えている」演出**（[ADR-007](architecture.md#adr-007-先輩が考えている演出でレイテンシを体験に変える)）
- [ ] セッション作成直後の先行診断キック（ADR-006）
- [ ] `202 Accepted` を受けた場合の再試行
- [ ] 原因宣言フォーム

### CD
- [ ] `deploy-function.yml` の `push` トリガーを有効化
- [ ] development 環境への自動デプロイ

**受け入れ条件**:
- development 環境にデプロイされた API に対し、実際のエラーを投げて Lv1〜Lv5 を通過し、
  原因宣言で `reached` 判定を受けられる
- 全画面・全レスポンスを通して答えが表示されない
- 最初の質問表示まで 5 秒以内（NFR-P1）

**MVP に入れないもの**: レポート / スコア / 履歴 / レート制限 / production 環境

## リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| **LLM が答えを漏らす** | 製品価値が消滅 | M1-A で最優先検証。役割分離 + LeakGuard + フォールバックテンプレートの三重防御 |
| **enebular の `event` 形式が非標準で Hono が使えない** | 実装量が増える | M1-B で早期に実測。ダメなら `event` を正規化する薄いアダプタを自作（ADR-009 に記載済み） |
| **タイムアウトが LLM 呼び出しに対して短すぎる** | 診断・レポート生成が完走しない | M1-B で実測（Q-5）。短い場合は診断を 2 リクエストに分割するか、より高速なモデルへ |
| **データストアのアクセス枠が先に枯れる** | 検証が止まる | フリー枠は約 185 セッション / 月と試算済み。M3 で実測し、必要なら削減策（Q-7）を適用 |
| **診断が外れる** | 見当違いの質問で学習にならない | `confidence` が低い場合は情報を補う質問に切り替える。レポートで診断が外れた旨を正直に出す |
| **質問が退屈 / 冗長** | 離脱 | 段階を 5 つに固定し、1 段階あたり最大 3 問で必ず前に進める |
| **待ち時間が長い** | 離脱 | 診断を別リクエストに分離（ADR-006）。待ち時間を「先輩が考えている」演出に変える（ADR-007） |
| **エラーに認証情報が混入** | 情報漏洩 | 保存前・送信前のマスキング（FR-13）を M2 の必須項目とする |
| **LLM コストが想定超過** | 運営不能 | 用途別モデル分離 + セッション単位のトークン上限 |
