---

## 全体像

```
 M0 要件定義      ← 現在地
 M1 技術検証      「答えを言わない」と enebular 実測。ここが崩れたら設計を変える
 M2 MVP           1 人が 3 ゲートを通しで体験できる。認証とテナントを含む
 M3 計測          スコアと個人ダッシュボード。ここで「学習サービス」として成立
 M4 組織機能      演習・問題集・組織ダッシュボード・評価レポート。ここで「BtoB 製品」になる
 M5 運用品質      公平性の検証・監査・レート制限。ここで「外部に売れる」
```

> **M3 までは個人体験、M4 で組織価値。** 順序を逆にしない。
> 利用者が使い続けてくれなければ、管理者が欲しいデータは 1 行も溜まらないため。

## M1: 技術検証（Spike）

**目的**: 製品が成立しなくなるリスクを、UI を作る前に潰す。

### 1-A. 「答えを言わない」がプロンプトで実現できるか（最重要）

- [ ] OrcaRouter 疎通（`GET /v1/models` でカタログ取得、用途別モデル ID を確定 → **Q-1**）
- [ ] Diagnoser の構造化出力（JSON Schema 準拠）を CLI で実行
- [ ] **Gate A のヒントが、答えを漏らさず着眼点だけを示せるか**
- [ ] Questioner に `focusHints` だけを渡し、答えを漏らさず出題できるか
- [ ] LeakGuard の検出ルールを実装し、代表 20 ケースで検証
- [ ] 実際のエラー 10 件で、Gate A → B → C を手動で通しでやってみる

**受け入れ条件**:
- 10 件中 8 件以上で、Gate A・B のすべての生成文に答えの漏洩がない
- Diagnoser の原因特定が 10 件中 7 件以上で妥当
- **Gate A のヒントだけで解けるケースが 10 件中 2 件以上ある**（ゲート設計の妥当性）

> **Gate A で誰も解けないなら、ヒントが弱すぎるか、そもそも 3 段階に分ける意味がない。**
> ここは体験と評価分解能の両方に効くため、必ず確かめる。

### 1-B. enebular 上で設計どおりに動くか

- [ ] **エコー関数をデプロイし、HTTP トリガーが渡す `event` の形式を確認**（→ **Q-6**）
- [ ] `hono/aws-lambda` の `handle()` で Hono アプリが動くか（→ ADR-009）
- [ ] esbuild バンドル ZIP がそのまま動くか（ワークスペース依存を含めて）（→ ADR-008）
- [ ] **タイムアウトの上限値**と、20 秒級の LLM 呼び出しが完走するか（→ **Q-5**）
- [ ] `bulk-update cloud-config` の `envVars` で環境変数が読めるか（→ **Q-8**）
- [ ] `connectDataStore` 有効時に `@uhuru/enebular-sdk` が認証なしで動くか
- [ ] `query` で、メインキー一致 + サブキー範囲・降順・`begins_with` が動くか
      （`org_directory` の `member#` 接頭辞検索に必要）
- [ ] ULID をサブキーにしたときの辞書順ソートが時系列順になるか
- [ ] コールドスタート時のレイテンシ実測（NFR-P1 の 5 秒に影響する）
- [ ] `enebular-cli` によるデプロイを GitHub Actions から 1 回通す

**受け入れ条件**: ZIP デプロイした Hono アプリが `GET /v1/health` を返し、
データストアへの put / get / query が動き、CI からのデプロイが成功する。

> 1-A と 1-B は依存関係がないため**並行して進めてよい**。

## M2: MVP（3 ゲートの一気通貫 + 認証 + CD）

**目的**: 1 人のエンジニアが、実務のエラーを投げて 3 ゲートを通しで体験できる。

### 基盤
- [ ] モノレポ初期化（pnpm workspaces + Turborepo）
- [ ] `packages/shared`: Zod スキーマ（API 契約）
- [ ] `packages/core`: **ゲート遷移** / 段階遷移 / マスキング / LeakGuard / ULID（**単体テスト付き**）
- [ ] `packages/datastore`: **`OwnerId` ブランド型**（ADR-010）+ 主要テーブルのリポジトリ
- [ ] `packages/llm`: OrcaRouter クライアント + Diagnoser / Hinter / Questioner / Judge / Revealer

### 認証とテナント（BtoB の前提）
- [ ] OIDC / GitHub OAuth のログインフロー（→ **Q-9**）
- [ ] 認証コンテキストの構築と `ownerId` の組み立て
- [ ] `org_directory`: 組織とメンバーの最小実装
- [ ] ロール判定ミドルウェア（`member` のみで可）

### バックエンド（apps/function）
- [ ] `POST /sessions`（Gate A のヒントを返す）, `POST /diagnose`（先行診断）
- [ ] `POST /hints`, `POST /advance`, `POST /answers`
- [ ] `POST /conclusion`, `POST /reveal`, `POST /retrospect`
- [ ] 冪等性の実装（FR-14）

### フロントエンド（apps/web）
- [ ] ログインとエラー投稿フォーム
- [ ] **Gate A のヒントパネル**（設問を出さない画面）
- [ ] **Gate B の設問カード**（選択肢 / 段階プログレス）
- [ ] **Gate C の解説パネル + 振り返り 1 問**
- [ ] 「先輩が考えている」演出（ADR-007）
- [ ] セッション作成直後の先行診断キック（ADR-006）と `202` 再試行

### CD
- [ ] `deploy-function.yml` の `push` トリガーを有効化、development へ自動デプロイ

**受け入れ条件**:
- development 環境で、実務のエラーを投げて Gate A → B → C を通しで体験できる
- Gate A・B の全画面・全レスポンスを通して答えが表示されない
- Gate A のヒント表示まで 5 秒以内（NFR-P1）

**MVP に入れないもの**: スコア / ダッシュボード / 演習 / 問題集 / 組織機能

## M3: 計測（"Metry" の実装）

**目的**: 学習が「やって終わり」にならないようにする。**個人向けとして成立する状態。**

- [ ] `packages/core/scoring.ts`: 5 軸スコア（**LLM 非依存の純関数**, NFR-Q4）
- [ ] `packages/core/normalization.ts`: 難易度正規化・成長率
- [ ] Reporter: 振り返りレポート生成 → `reports` テーブルへ保存
- [ ] **`scoreExplanation`**（算出根拠）をレポートに含める（NFR-F1）
- [ ] `member_stats` の更新（ADR-011）と `GET /report` の冪等性
- [ ] 振り返り画面（レーダー / つまずき / 一般化された学び）
- [ ] 個人ダッシュボード（到達ゲート分布・5 軸推移・成長率）
- [ ] ゲート遷移条件の調整（→ **Q-3 / Q-4**）
- [ ] データストアのアクセス回数を実測し、削減の要否を判断（→ **Q-7**）

**受け入れ条件**:
- 3 セッション実施後、個人ダッシュボードで軸別の弱点が読み取れる
- **利用者が自分のスコアの算出根拠を画面で確認できる**
- 「一般化された学び」が、次回に転用できる抽象度で出力される

## M4: 組織機能（BtoB 製品として成立させる）

**目的**: 管理者が「導入する理由」を得る。**ここで初めて BtoB 製品になる。**

### 演習と問題集
- [ ] `question_bank`: 問題の登録・編集・タグ付け（FR-34）
- [ ] 演習モードのセッション（`question_bank` の診断を使い Diagnoser を呼ばない）
- [ ] `assignments`: 割り当てと進捗管理（FR-36 / FR-37）
- [ ] **実務セッション → 問題集の変換**と匿名化（FR-35 / → **Q-13**）
- [ ] 難易度の設定（v1 は手動 / → **Q-10**）

### 組織
- [ ] ロール管理（`member` / `lead` / `admin`）と閲覧範囲制御（NFR-S6）
- [ ] メンバー招待・チーム設定
- [ ] **組織ダッシュボード**（`member_stats` を 1 クエリで集計）
- [ ] **組織の弱点サマリを初期表示**にする（evaluation-model.md §5.2）
- [ ] 組織設定（ランキング可否・保持期間）
- [ ] ランキング（既定 無効 / → **Q-11**）
- [ ] **評価レポート出力**（FR-27 / → **Q-12**）

**受け入れ条件**:
- 管理者が組織ダッシュボードを開き、組織の弱い軸を 3 秒以内に把握できる（NFR-P4）
- 10 名に演習を割り当て、同一問題での比較ができる
- 評価レポートが成長率を先頭に、5 軸内訳と算出根拠つきで出力される
- **総合点だけのレポートが出力できないことを確認する**（NFR-F5）

## リスクと対策

### プロダクトのリスク

| リスク | 影響 | 対策 |
|---|---|---|
| **LLM が答えを漏らす** | 製品価値が消滅 | M1-A で最優先検証。役割分離 + LeakGuard + フォールバックテンプレートの三重防御 |
| **Gate A で誰も解けない** | 3 段階に分ける意味がなくなる | M1-A の受け入れ条件に含める。ヒントの強度を調整 |
| **利用者が使わなくなる** | 評価データが溜まらず、BtoB 価値が消える | 業務支援を最優先（P2）。開示を罰しない。M3 までは個人価値に集中する |
| **「監視ツール」と受け取られる** | 現場の反発で導入が頓挫 | 自分のデータは常に自分が見られる。監査ログ。導入時に運用方針を合意（evaluation-model.md §8） |
| **評価に使った途端に指標が歪む** | 学習効果も評価妥当性も壊れる | 難易度正規化・成長率主義・実務モードは非比較・開示の減点を小さく（evaluation-model.md §4） |
| **診断が外れる** | 見当違いの問いで学習にならない | `confidence` が低い場合は情報を補う質問に切り替える。レポートで正直に出す |

### 技術のリスク

| リスク | 影響 | 対策 |
|---|---|---|
| **enebular の `event` 形式が非標準で Hono が使えない** | 実装量が増える | M1-B で早期に実測。ダメなら正規化アダプタを自作（ADR-009 に記載済み） |
| **タイムアウトが LLM 呼び出しに対して短すぎる** | 診断・レポート生成が完走しない | M1-B で実測（Q-5）。短い場合は分割か高速モデルへ |
| **`member_stats` の二重加算で評価データが壊れる** | 評価の信頼性が失われる | `GET /report` を冪等に（api-spec.md §4）。`reports` から再構築可能にしておく |
| **テナント間のデータ漏洩** | **事業が終わる** | キー設計 + ブランド型で構造的に防ぐ（ADR-010）。M5 でテストによる保証 |
| **データストアのアクセス枠** | 大規模導入で頭打ち | エンタープライズで約 51,000 セッション / 月。1,000 名超で要監視。削減策は Q-7 |
| **待ち時間が長い** | 離脱 | 診断を別リクエストに分離（ADR-006）。「先輩が考えている」演出（ADR-007） |
| **エラーに認証情報が混入** | 情報漏洩 | 保存前・送信前のマスキング（FR-11）を M2 の必須項目とする |
| **問題集への匿名化漏れ** | 顧客情報が社内に拡散 | 登録は `draft` から。人の目視確認を必須（Q-13） |
