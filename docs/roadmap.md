# v0.1 — 5 日間の計画

実装対象は [scope-v0.1.md](scope-v0.1.md) が正。

## 進め方の原則

| # | 原則 | 理由 |
|---|---|---|
| 1 | **Day 1 に「デプロイして動く」状態を作る** | 最後にまとめてデプロイすると、詰まったときに逃げ場がない |
| 2 | **外部依存の不明点を最初に潰す** | enebular の `event` 形式・タイムアウト・OrcaRouter のモデル ID。**ここで詰まると全部が止まる** |
| 3 | **MOCK モードを Day 2 に作る** | 以降 3 日間の開発速度とデモの安全性がここで決まる |
| 4 | **毎日終わりに「通しで動く」状態を保つ** | 未完成の枝を持ち越さない。Day 5 に統合作業を残さない |
| 5 | **1 日ごとに削る判断をする** | 遅れたら翌日に持ち越さず、その場でスコープを削る |

## Day 1 — 土台（外部依存の不確実性を消す）

**この日のゴール**: デプロイした URL で `Hello` が表示され、データストアに 1 件書ける。

### 午前 — 外部依存の実測（最優先）

- [ ] OrcaRouter 疎通。`GET /v1/models` でカタログ取得し、**高品質 / 安価のモデル ID を確定**（→ Q-1）
- [ ] エコー関数を ZIP デプロイし、**HTTP トリガーが渡す `event` の形式を確認**（→ Q-6）
- [ ] **タイムアウトの上限値**を確認し、20 秒級の処理が通るか確かめる（→ Q-5）
- [ ] `envVars` で環境変数が読めるか（→ Q-8）
- [ ] `connectDataStore` + `@uhuru/enebular-sdk` で put / get / query が動くか

> **午前でここが崩れたら、その場で設計を変える。**
> `event` が非標準なら正規化アダプタを書く。タイムアウトが短ければ処理を分割する。
> **Day 4 に発覚すると手遅れになる項目を、初日の午前に置いている。**

### 午後 — 骨組み

- [ ] モノレポ初期化（pnpm workspaces + Turborepo）

## 遅れたときに削る順序

上から順に削る。**下 3 つは削らない。**

| 順 | 削る対象 | 影響 |
|---:|---|---|
| 1 | 履歴一覧の画面（API だけ残す） | 1 セッションのデモには影響しない |
| 2 | 5 軸スコアのレーダー表示 → 数値のリスト表示 | 見栄えは落ちるが情報は伝わる |
| 3 | Gate A のヒント Lv2 / Lv3 → Lv1 のみ | ゲート構造自体は残る |
| 4 | Gate B の段階を Lv1〜5 → Lv1〜3 | 5 軸スコアが 3 軸になる |
| 5 | 簡易ログイン → 固定ユーザー | **F15 Must だが、コアが動かないよりまし** |
| — | **3 ゲートの貫通** | ❌ 削らない。これが製品そのもの |
| — | **LeakGuard とマスキング** | ❌ 削らない。壊れると製品価値と安全性が消える |
| — | **MOCK モード** | ❌ 削らない。デモの保険 |

## リスクと対策

### プロダクトのリスク

| リスク | 影響 | 対策 |
|---|---|---|
| **LLM が答えを漏らす** | 製品価値が消滅 | M1-A で最優先検証。役割分離 + LeakGuard + フォールバックテンプレートの三重防御 |
| **Gate A で誰も解けない** | 3 段階に分ける意味がなくなる | M1-A の受け入れ条件に含める。ヒントの強度を調整 |
| **利用者が使わなくなる** | 評価データが溜まらず、BtoB 価値が消える | 業務支援を最優先（P2）。開示を罰しない。M3 までは個人価値に集中する |
| **「監視ツール」と受け取られる** | 現場の反発で導入が頓挫 | 自分のデータは常に自分が見られる。監査ログ。導入時に運用方針を合意（evaluation-model.md §8） |
| **評価に使った途端に指標が歪む** | 学習効果も評価妥当性も壊れる | 難易度正規化・成長率主義・実務モードは非比較・開示の減点を小さく（evaluation-model.md §4） |
| **診断が外れる** | 見当違いの問いで学習にならない | `confidence` が低い場合は情報を補う質問に切り替える。レポートで正直に出す |

### 技術のリスク

| リスク | 影響 | 対策 |
|---|---|---|
| **enebular の `event` 形式が非標準で Hono が使えない** | 実装量が増える | M1-B で早期に実測。ダメなら正規化アダプタを自作（ADR-009 に記載済み） |
| **タイムアウトが LLM 呼び出しに対して短すぎる** | 診断・レポート生成が完走しない | M1-B で実測（Q-5）。短い場合は分割か高速モデルへ |
| **`member_stats` の二重加算で評価データが壊れる** | 評価の信頼性が失われる | `GET /report` を冪等に（api-spec.md §4）。`reports` から再構築可能にしておく |
| **テナント間のデータ漏洩** | **事業が終わる** | キー設計 + ブランド型で構造的に防ぐ（ADR-010）。M5 でテストによる保証 |
| **データストアのアクセス枠** | 大規模導入で頭打ち | エンタープライズで約 51,000 セッション / 月。1,000 名超で要監視。削減策は Q-7 |
| **待ち時間が長い** | 離脱 | 診断を別リクエストに分離（ADR-006）。「先輩が考えている」演出（ADR-007） |
| **エラーに認証情報が混入** | 情報漏洩 | 保存前・送信前のマスキング（FR-11）を M2 の必須項目とする |
| **問題集への匿名化漏れ** | 顧客情報が社内に拡散 | 登録は `draft` から。人の目視確認を必須（Q-13） |
