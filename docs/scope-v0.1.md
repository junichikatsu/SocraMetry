## 1. この期間で証明したいこと

5 日で全機能は作れない。**何を証明するかを 1 つに絞る。**

> **「AI に答えを出させるのではなく、AI に問いを出させることで、
> 人が自力でバグに到達できる」**——これが体験として成立することを示す。

この 1 点に効かないものは、Must でも削る候補として扱う。

### 削るときの優先順位

| 順位 | 判断基準 |
|---:|---|
| 1 | **動かないより、少なく動く。** 機能を足して不安定になるくらいなら削る |
| 2 | **コア体験 > 周辺機能。** 問答が成立しないなら履歴もスコアも意味がない |
| 3 | **説明できるもの > 多いもの。** 設計判断を語れない機能は価値が半減する |

## 3. 作るもの（v0.1 の確定スコープ）

### 3.1 コア体験 — 3 ゲートを 1 画面で

[3 ゲート方式](requirements.md#23-3-ゲート方式--段階的な開示)をそのまま実装する。
**ページ遷移なし。** 1 枚の HTML の中で状態が進む。

```
 ┌─ 1 画面 ────────────────────────────────────────────┐
 │                                                      │
 │  [エラーを貼り付け]  ──▶  Gate A: ヒント             │
 │                              │                       │
 │                              ▼                       │
 │                          Gate B: 設問 → 回答 → 設問   │
 │                              │                       │
 │                              ▼                       │
 │                          Gate C: 解説 + 振り返り      │
 │                              │                       │
 │                              ▼                       │
 │                          結果: 5 軸スコア + 学び      │
 └──────────────────────────────────────────────────────┘
```

### 3.2 2 段階の LLM（F01）

**この 2 段構造が、この製品が AI でなければ成立しない理由そのもの**である。

| 段 | 役割 | モデル | 呼び出し回数 / セッション |
|---|---|---|---|
| **1 段目** | **Diagnoser** — 原因を特定する（ユーザーには見せない） | **高品質** | 1 回 |
| **2 段目** | **Hinter / Questioner** — 結論を渡されずに、着眼点だけから問いを作る | **安価** | 10〜15 回 |

1 段目の出力のうち **`focusHints`（着目点）だけ**を 2 段目に渡し、
`rootCause`（結論）は渡さない。**2 段目は答えを知らない状態で問いを作る。**

> 単一プロンプトで「原因を特定しつつ絶対に言わない」を両立させると必ず漏れる。
> 役割を分けて情報を絞ることで、漏洩を確率ではなく設計で防ぐ。
> 詳細は [socratic-engine.md](socratic-engine.md)。

### 3.3 実装する機能

| 機能 | 内容 |
|---|---|
| 簡易ログイン | メール + パスワード（scrypt）+ JWT Cookie。**招待コード制**（→ §4.2） |
| エラー投稿 | テキスト貼り付け。最大 20,000 文字。マスキング後に保存 |
| 先行診断 | セッション作成とは別リクエストで実行（[ADR-006](architecture.md#adr-006-sse-を廃止し診断の先行実行で体感速度を確保する)） |
| Gate A | ヒント Lv1〜3 の段階開放 |
| Gate B | Lv1 観察 → Lv5 修正 の選択式設問。同段階 3 問まで |
| Gate C | 原因・根拠・修正方針・再発防止策の開示 + 振り返り 1 問 |
| 原因宣言 | 自由記述 → 到達判定（reached / partial / not_reached） |
| LeakGuard | 決定的ルールによる漏洩検査 + 1 回だけ再生成 + 定型フォールバック |
| マスキング | API キー / トークン / メール / 絶対パスの除去 |
| スコア | 5 軸 + 到達ゲート。**純関数**（LLM 非依存） |
| 履歴 | セッション一覧とスコア推移（自分の分のみ） |
| **MOCK モード** | LLM を呼ばず固定応答。デモの保険 + 開発の高速化 |
| コストログ | 1 リクエストごとに model / tokens / 推定単価を構造化ログへ |

## 4. 5 日で完走するための設計判断

期間が短いことを理由に品質を落とすのではなく、**リスクの高い構成要素を構造的に消す**。

### 4.1 フロントエンドを関数から同一オリジンで配信する

**決定**: フレームワークを使わず HTML + CSS + 素の JavaScript で書き、
**enebular クラウド実行環境の関数がそのまま静的ファイルを返す**。

```
  ✗ 別オリジン構成            Vercel(HTML) ──CORS──▶ enebular(API)
                                    ↑ CORS 設定・SameSite=None・デプロイ 2 系統

  ✓ v0.1 の構成               enebular ─┬─ GET  /          → index.html
                                        ├─ GET  /app.js    → app.js
                                        └─ POST /v1/...    → API
```

**これで消える作業とリスク**

| 消えるもの | 理由 |
|---|---|
| CORS 設定 | 同一オリジンになる |
| `SameSite=None` の Cookie 問題 | 同一オリジンなら `Lax` で足りる |
| デプロイ先 2 系統の管理 | ZIP 1 つで完結する |
| `NEXT_PUBLIC_API_BASE_URL` の環境差異 | 相対パス `/v1/...` で済む |
| ビルドツールチェーンの学習・設定 | esbuild だけになる |

**5 日という期間で、最も費用対効果の高い削減。**
機能を削らずに、作業とリスクだけを削っている。
詳細は [ADR-012](architecture.md#adr-012-フロントエンドを関数から同一オリジンで配信する)。

### 4.2 認証を最小構成にする

**決定**: 外部 IdP（OIDC / OAuth）を使わず、メール + パスワード + 招待コード。

| 項目 | 選択 | 理由 |
|---|---|---|
| 方式 | メール + パスワード | OAuth のコールバック URL 設定・アプリ登録・リダイレクト検証が不要 |
| ハッシュ | `node:crypto` の scrypt | 外部依存ゼロ。Lambda で追加パッケージ不要 |
| セッション | JWT (HS256) を HttpOnly Cookie | ステートレスで Lambda と相性が良い |
| 登録 | **招待コード必須**（環境変数） | 公開 URL に無制限のサインアップを置かない。LLM コストの流出防止も兼ねる |

> **OAuth を選ばなかったのは技術的な難しさではなく、外部設定への依存を減らすため。**
> 5 日間で「他所の設定が原因で動かない」時間を作らない。
> 本来の BtoB 構成（SSO）は v0.2 で載せる（[ADR-004](architecture.md#adr-004-認証を-v1-の必須要件とするbtob-化に伴う改訂)）。

### 4.3 MOCK モードを最初に作る

**決定**: `MOCK_MODE=true` で LLM を一切呼ばず、固定の診断・ヒント・設問を返す。

| 効く場面 | 効果 |
|---|---|
| UI 開発 | LLM の応答を待たずに全画面を通せる。**開発速度が数倍になる** |
| 自動テスト | 決定的な応答になり、主要導線のテストが書ける（F13） |
| コスト | 開発中の LLM 課金がゼロになる |
| **デモ** | 通信障害・レート制限・モデル障害があっても**デモが止まらない** |

**Day 2 の早い段階で入れる。** 後から入れると、
LLM 呼び出しがコードの各所に散った後になり、差し込みが高くつく。

### 4.4 データストアのテーブルを 5 つに絞る

マルチテナント（F16 Won't）を落とすため、キー設計を単純化する。

| # | テーブル | メインキー | サブキー | v0.1 | 備考 |
|---|---|---|---|---|---|
| 1 | `users` | `email` | `"account"` | ✅ | 簡易ログイン用 |
| 2 | `sessions` | `ownerId` | `sessionId` (ULID) | ✅ | セッション本体 + 全ターン |
| 3 | `session_secrets` | `sessionId` | `kind` | ✅ | 診断と正解（★非公開） |
| 4 | `reports` | `ownerId` | `sessionId` (ULID) | ✅ | レポート + スコア |
| 5 | `ops_logs` | `sessionId` | `ts` | ✅ | **コストログ**（F11） |
| — | `org_directory` / `member_stats` / `assignments` / `question_bank` | | | ❌ | v0.2（F16 Won't） |

**`ownerId` は v0.1 では `usr_<id>`。** v0.2 でテナントを入れる際に
`<tenantId>:<memberId>` へ拡張する。**キー名を今のうちに `ownerId` にしておく**ことで、
拡張時にテーブル定義とクエリの形を変えずに済む。今この命名にするコストはゼロ。

> `ops_logs` は元の設計では既定で無効だったが、
> **v0.1 ではコスト実測（F11）のため有効にする**。フリー枠での検証中は
> セッション数が少ないため、アクセス枠への影響は問題にならない。

## 5. 作らないもの（と、その理由）

| 項目 | 理由 |
|---|---|
| **マルチテナント・権限管理**（F16） | v0.1 で証明したいのは「問答が成立するか」。組織機能はその後 |
| **演習モード・問題集・割り当て** | 同上。実務モード 1 本に絞る |
| **組織ダッシュボード・ランキング・評価レポート** | 同上 |
| **成長率・難易度正規化・time_index** | セッション数が溜まらないと意味のある値が出ない |
| **レスポンシブ**（F17） | PC 前提。閲覧環境を絞ることでレイアウト検証の工数を削る |
| **独自ドメイン・本番インフラ**（F19） | enebular の HTTP トリガー URL をそのまま使う |
| **RAG・ベクトル DB**（F18） | **→ 下記** |
| ストリーミング表示 | 実行環境の制約で原理的に不可（[E1](architecture.md#2-enebular-採用にともなう-4-つの制約)） |

### RAG を採用しない判断（F18）

RAG は「モデルが知らない情報を渡す」ための技術である。
本製品で LLM に渡すべき情報は、**ユーザーがその場で貼り付けたエラーテキストとコード断片**であり、
これは最初からプロンプトに入っている。**検索して補う対象が存在しない。**

| 検討した使い道 | 不採用の理由 |
|---|---|
| 過去の類似エラーを検索して診断精度を上げる | 過去データが溜まっていない。v0.1 時点で検索対象がゼロ |
| 社内ドキュメントを参照して問いを作る | 社内問題集（v0.2）が前提。今は存在しない |
| フレームワーク固有の知識を補う | モデルが既に持っている。RAG を挟むと精度が下がる可能性の方が高い |

**データが溜まってから再評価する。**
v0.2 で社内問題集が実装され、実務セッションが蓄積された段階で、
「類似の過去セッションを検索して診断の補助にする」用途に価値が出る可能性がある。

> 使える技術だから使う、という判断はしない。
> **解いている問題に対して必要かどうかで決める。**

## 7. 完了の定義（Definition of Done）

v0.1 が完成したと言えるのは、以下がすべて満たされたとき。

| # | 条件 |
|---|---|
| 1 | デプロイ済みの URL で、ログインからスコア表示まで通しで動く |
| 2 | Gate A・B の全画面・全レスポンスを通して**答えが表示されない** |
| 3 | エラー投稿から Gate A のヒント表示まで **5 秒以内** |
| 4 | LLM 障害・不正入力・タイムアウトのいずれでも**画面が止まらず、原因が表示される** |
| 5 | `MOCK_MODE=true` で LLM なしに全導線が動く |
| 6 | 1 セッションの実測コストが記録され、コスト表に反映されている |
| 7 | README だけを読んで、他人が **API キーなしに `MOCK_MODE=true` でローカル起動できる** |
| 8 | 主要導線の自動テストが通る |

> **#7 は #5 と組み合わせて定義している。** 審査員や第三者は OrcaRouter の API キーを持たないため、
> 「起動できる」を実 LLM 前提で書くと**原理的に満たせない条件**になる。
> README のセットアップ手順も `MOCK_MODE=true` を既定とし、
> **clone してすぐ動く状態**を出発点にする。実 LLM は「キーがある場合」の追加手順として後ろに置く。
