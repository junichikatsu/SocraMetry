## 1. この版で証明したいこと

v0.1 が証明したのは「**問いによって自力到達できる**」という個人の体験である。
v0.2 で証明するのは、その先にある **BtoB としての導入理由**である。

> **「同一条件の演習と成長率によって、デバッグ能力の評価が組織で成立する」**
> ——管理者（P-1）が、印象でも自己申告でもないデータで育成と評価を語れる状態を示す。

この 1 点に効かないものは、v0.2 でも削る候補として扱う。

### v0.1 との関係

| 版 | 証明すること | 主役 |
|---|---|---|
| v0.1 | 問いで自力到達できる（学習体験の成立） | P-2 利用者 |
| **v0.2** | **同一条件の比較と成長率で評価が成立する（組織価値の成立）** | **P-1 管理者 / P-3 運用者** |

> **順序を逆にしない**（[roadmap.md](roadmap.md)）。利用者が使い続けなければ
> 管理者の欲しいデータは 1 行も溜まらない。v0.2 でも P2（業務支援を最優先）は変わらない。

### 削るときの優先順位（v0.1 から変更なし）

| 順位 | 判断基準 |
|---:|---|
| 1 | **動かないより、少なく動く** |
| 2 | **コア価値 > 周辺機能。** v0.2 のコアは「演習による横比較」と「成長率」 |
| 3 | **説明できるもの > 多いもの** |

## 3. 実装フェーズ — 依存関係で 4 段に分ける

**すべての v0.2 機能はテナント分離の上に載る。** 基盤を最初に固め、
「演習 → 可視化 → 運用品質」の順で価値が出る単位ごとに区切る。

```
 Phase 1  基盤        テナント分離・org_directory・認証の組織対応・ロール
    │                 ─ ここが終わるまで他のフェーズに着手しない ─
    ▼
 Phase 2  演習        question_bank・演習モード・assignments
    │                 ─ ここで「同一条件の比較」が成立する ─
    ▼
 Phase 3  可視化      member_stats・成長率・組織ダッシュボード・評価レポート・ランキング
    │                 ─ ここで「導入する理由」が完成する ─
    ▼
 Phase 4  運用品質    監査ログ・データ削除・production 分離・公平性の実地検証
                      ─ ここで「外部に提供できる」（M5）─
```

| Phase | 含まれる要件 | 完了の目印 |
|---|---|---|
| 1 基盤 | FR-30 / 31 / 32 / 33 / 40, NFR-S5 / S6 | **他組織のデータが取得できないことがテストで保証されている** |
| 2 演習 | FR-34 / 36 / 37, UC-08,（FR-35） | 10 名に演習を割り当て、同一問題の結果を比較できる |
| 3 可視化 | FR-25 / 26 / 38, NFR-C6,（FR-27 / 39） | ダッシュボードが 3 秒以内に組織の弱点を示す（NFR-P4） |
| 4 運用品質 | NFR-S7 / S9 / O5,（FR-41, NFR-O3） | 導入企業に本番提供できる状態（M5 受け入れ条件） |

> **Phase 1 を最初に置く理由**: `ownerId` の形式（`<tenantId>:<memberId>`）は
> 全テーブル・全リポジトリ関数の引数に波及する。後から入れると
> v0.2 で書いたコードすべてを書き直すことになる。
> 逆に Phase 2 と 3 は、Phase 1 さえあれば互いに独立して進められる。

## 4. 設計判断

### 4.1 v0.1 の個人データは v0.2 に移行しない

**決定**: v0.1（`ownerId = "usr_<id>"`、テナントなし）のセッション・レポートは、
v0.2 のテナント環境へ**移行しない**。移行バッチも作らない。

| 根拠 | 説明 |
|---|---|
| v0.1 は検証利用 | 招待制の限定公開（A-6）であり、データは開発チームの検証セッションが主 |
| 評価データとして使えない | v0.1 のセッションはすべて `comparable: false` 相当。移行しても評価には算入できない（[data-model.md §6](data-model.md#6-テナント分離の強制nfr-s5) のデモ移行と同じ理由） |
| 移行コストが利益を上回る | read → put → delete でアイテム数 × 2 のアクセスを消費する。得られるのは検証データの引っ越しだけ |

**`users` テーブルは v0.2 の SSO / 組織移行をもって役目を終える**
（[data-model.md §3.9](data-model.md#39-users--簡易ログインのアカウントv01)）。
アカウントは `org_directory` の `member#<memberId>` に作り直す。
メンバーには新しい組織テナントで登録し直してもらう。

> どうしても引き継ぎたいセッションが出た場合のみ、
> [data-model.md §6](data-model.md#6-テナント分離の強制nfr-s5) の
> read → put → delete 手順を個別に流用する（`comparable: false` のまま）。

### 4.2 認証は「組織対応した簡易認証」から始め、SSO はプロバイダ差し替えで載せる

**決定**: FR-31 の Must は「**組織メンバーとして認証できること**」と解釈する。
方式は次の 2 段階で満たす。

| 段階 | 方式 | 版内優先度 |
|---|---|---|
| 1 | **メール + パスワード + 組織招待**（v0.1 の簡易認証を組織対応に拡張） | Must |
| 2 | **OIDC（SSO）** — 認証プロバイダを差し替えられる抽象の上に 1 プロバイダ実装 | Should（Q-9 の回答で確定） |

| 根拠 | 説明 |
|---|---|
| Q-9 が未解消 | SSO 必須か GitHub OAuth で足りるかは**初期導入企業へのヒアリング**で決めるとしている（[requirements.md §9.2](requirements.md#92-v02-以降で解消するもの)）。回答前に SSO を作り込むと、要らない方を作るリスクがある |
| v0.1 の資産が使える | scrypt + JWT Cookie の実装は動いており、変更点は「`users` → `org_directory` の照合」と「トークンへの `tenantId` / `role` の同梱」に絞れる |
| 段階 1 だけでもテナント分離は完全 | テナント分離は認証方式ではなく **キー設計とブランド型**で守る（NFR-S5）。SSO の後回しがセキュリティの後回しにはならない |

**実装上の要点**: 認証コンテキスト（`tenantId` / `memberId` / `role` / `teamId`）の
**取り出し口を 1 箇所に抽象化**し、credential 認証と OIDC のどちらで入っても
同じコンテキストが出てくる形にする。ルート・リポジトリ層は認証方式を知らない。

### 4.3 Gate A の 5 軸は「参考値」として表示し、成長率の算出から除く

**決定**: [evaluation-model.md §4.6](evaluation-model.md#46-既知の限界--gate-a-では-5-軸が機能しない) の
3 案のうち、**案 B を v0.2 の暫定仕様として採用する**。

| 案 | 内容 | 判断 |
|---|---|---|
| A | Gate A は 5 軸を出さない | 表示が不揃いになり、履歴・ダッシュボードの実装が分岐だらけになる |
| **B** | **5 軸は出すが「参考値」と明示し、成長率の算出から除く** | **採用。** 表示は揃い、評価値の汚染も防げる |
| C | Gate A 到達後に振り返り設問を出して観測値を得る | 解決した人を引き止める。P2（業務支援優先）と衝突 |

v0.2 は評価（成長率・レポート・ダッシュボード）を組織に見せる版であり、
「Gate A の 5 軸は他と意味が違う」問題を**未決のまま評価に載せることはできない**。
実データが溜まった段階で案 C の追加やヒント係数の見直しを再評価する。

**実装**: `reports.score` に `axesReliable: boolean` を追加し、
Gate A（設問 0 問）のセッションは `false` とする。成長率（FR-26）と
`member_stats.recentAxes` / `previousAxes` の集計は `axesReliable: true` のみを対象にする。
UI とレポートには「参考値」の注記を出す（NFR-F1: 数値の意味が変わることを隠さない）。

### 4.4 公平性はデータ構造とテストで守る（運用ルールにしない）

v0.2 から NFR-F1〜F6 が適用される。v0.1 と同じ思想で、**人の注意力に頼らない**。

| 要件 | 構造での担保 |
|---|---|
| 実務モードを横比較しない（NFR-F2） | ランキング・組織比較のクエリは `comparable: true` しか読まない（実装済みのフィールドを使う） |
| 総合点だけのレポートを出さない（NFR-F5） | 評価レポートのレスポンス型に**総合点フィールドを定義しない**（[api-spec.md §3.15](api-spec.md#315-post-v1orgreportsevaluation--評価レポート出力fr-27)） |
| 開示を減点の主因にしない（NFR-F4） | `gate_factor` は実測で成立を確認済み（[evaluation-model.md §3.5](evaluation-model.md#35-実測されたスコアv01--2026-08-11)）。**ヒント係数の再評価**を Phase 3 の確認項目に含める |
| 算出根拠の開示（NFR-F1） | `scoreExplanation` は v0.1 実装済み。ダッシュボード・レポートにも同じ内訳を出す |
| 異議申し立て（NFR-F6） | セッション単位の報告 API（[api-spec.md §2.1](api-spec.md#21-問答3-ゲート)）。v0.2 は記録と管理者への表示まで |

### 4.5 匿名化は「自動マスキング + 人の確認」を必須とする（FR-35）

実務セッション → 問題集の変換で、固有名詞の自動除去精度は未検証（Q-13）。
v0.2 では**構造で守る**。

| # | ルール |
|---|---|
| 1 | 登録は必ず `draft` で始まる。`published` にするには**登録者による目視確認**を要求する（[api-spec.md §3.14](api-spec.md#314-post-v1problemsfrom-sessionsessionid--実務問題集fr-35)） |
| 2 | 変換時に FR-11 の決定的マスキング + FR-41 の組織辞書を**再適用**する（保存時から辞書が更新されている可能性があるため） |
| 3 | LLM による汎用化（変数名の一般化・文脈の削ぎ落とし）は**候補の生成まで**。確定は人が行う |

### 4.6 フロントエンドはフレームワーク導入を再検討する

[architecture.md ADR-013](architecture.md) は「v0.1 の 1 画面には過剰」という判断であり、
将来にわたる不要判断ではない。v0.2 は**画面の性質が変わる**。

| | v0.1 | v0.2 |
|---|---|---|
| 画面数 | 1 画面（問答） | 問答 + 問題集管理・割り当て・組織ダッシュボード・設定・レポート |
| 主な UI | ウィザード型の状態遷移 | **一覧・フォーム・グラフ・権限別の出し分け** |

**決定**: Phase 1 の間に技術選定をやり直す（issue #27 と統合して判断する）。
判断基準は 02_スキルマップの原則（経験のない技術を選ばない）に従い、
**React が第一候補**（チーム内に実務経験あり）。同一オリジン配信（ADR-012）は
ビルド成果物を関数から配る形で維持できるため、前提にしない理由はない。

### 4.7 組織のプロビジョニングはセルフサービスにしない

**決定**: v0.2 では組織（テナント）の作成 UI / API を**作らない**。
運営者が enebular コンソール（またはスクリプト）で `org_directory` に
`meta` と最初の `admin` メンバーを作成し、管理者に招待を渡す。

| 根拠 | 説明 |
|---|---|
| BtoB の導入は契約から始まる | セルフサインアップの需要がない（A-9）。作っても使われない |
| 課金がまだない | プラン管理（v0.2 でも Won't）なしのセルフサインアップは無制限利用の入口になる |
| 導入時合意と一体 | [evaluation-model.md §8](evaluation-model.md#8-導入時に合意すべきこと) の運用合意を経ずに組織を作らせない |

### 4.8 テーブルは 9 つ・エンタープライズプラン前提（A-10）

v0.2 で `org_directory` / `member_stats` / `assignments` / `question_bank` を追加し
9 テーブルになる。フリー枠（10）にも収まるが、アクセス回数の月次上限があるため
**本番提供はエンタープライズプラン前提**とする。`ops_logs` は v0.2 から**既定で無効**
（`OPS_LOG_ENABLED=false`）にし、コストログは実行環境の構造化ログへ寄せる
（[data-model.md §3.8](data-model.md#38-ops_logs--llm-呼び出しログnfr-o2)）。

## 5. 作らないもの（v0.2 の Won't）

| 項目 | 行き先 | 理由 |
|---|---|---|
| 組織テナントのセルフサインアップ | v0.3 以降 | §4.7 |
| 課金 / プラン管理 | v0.3 以降 | 初期導入は個別契約。課金基盤は導入実績の後 |
| 監査ログの閲覧 UI | v2 | 記録（NFR-S9）はする。画面はログ出力で代替できる |
| 難易度の自動算出 | v2 | 実績（正答率）が溜まってから（Q-10）。v0.2 は手動設定 |

## 8. 完了の定義（Definition of Done）

v0.2 が完成したと言えるのは、以下がすべて満たされたとき。

| # | 条件 | 対応 |
|---|---|---|
| 1 | 組織を作成し、管理者がメンバー 2 名以上を招待してログインできる | FR-30/31/33 |
| 2 | **他組織のデータが API からもリポジトリ層からも取得できないことが、自動テストで保証されている** | NFR-S5 |
| 3 | `member` が他人の個票を見られず、`lead` が自チームのみ、`admin` が組織全体を見られる | NFR-S6 |
| 4 | 問題を登録し、チームに割り当て、複数メンバーが演習モードで解き、**同一問題の結果を並べて比較できる** | FR-34/36, UC-08 |
| 5 | 組織ダッシュボードが **3 秒以内**に表示され、初期表示が組織の弱点サマリである | FR-38, NFR-P4 |
| 6 | 評価レポートが**成長率を先頭に**、5 軸内訳・組織平均・算出根拠つきで出力され、**総合点だけの出力ができない** | FR-27, NFR-F5 |
| 7 | Gate A のセッションが成長率の算出に混入しない（参考値の注記が表示される） | §4.3 |
| 8 | 評価データの閲覧（個票を含むダッシュボード・レポート出力）が監査ログに記録される | NFR-S9 |
| 9 | セッション・退職者・組織のデータ削除が実行でき、`member_stats` が `reports` から再構築できる | NFR-S7 |
| 10 | ランキングが既定で無効であり、有効化しても実務モードのスコアが混入しない | FR-39, NFR-F2 |
| 11 | v0.1 の全機能（3 ゲート・スコア・履歴・MOCK・コストログ）が退行していない | 既存テスト 216 件 + 追加分 |

> **#2 が v0.2 の生命線。** テナント間のデータ漏洩は「事業が終わる」リスク
> （[roadmap.md リスク表](roadmap.md#リスクと対策)）であり、
> 機能がいくら揃っていても #2 なしでは外部提供できない。
