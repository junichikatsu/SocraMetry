# ソクラテス式エンジン仕様

| 項目 | 内容 |
|---|---|
| ドキュメント版数 | v0.1 |
| 作成日 | 2026-08-09 |
| 関連 | [要件定義書](requirements.md) / [アーキテクチャ](architecture.md) |

本製品の中核。**「原因を分かっているのに、絶対に言わない」**をどう実現するかを定義する。

---

## 1. 設計の核心

LLM に「原因を特定して、でも答えは言わないで質問して」と 1 回で頼むと、**必ず漏れる**。
「〜が undefined になっているようですね。では…」のように、前置きで答えを言ってしまう。

そこで **役割を分離し、出題側に結論を渡さない**。

```
                 ┌──────────────────────────────────┐
  エラー入力 ───▶ │  ① Diagnoser（内部診断）           │
                 │  原因・根拠・確信度を特定する        │
                 │  出力はサーバ内部にのみ保持          │
                 └────────────┬─────────────────────┘
                              │
                    ┌─────────┴──────────┐
                    │  結論は渡さない       │  ← ここが設計の要
                    │  「着目点」だけ渡す    │
                    ▼                     
                 ┌──────────────────────────────────┐
  質問 ◀──────── │  ② Questioner（出題）              │
                 │  段階 Lv に応じた選択式の問いを作る  │
                 └──────────────────────────────────┘
                              ▲
  ユーザーの回答 ─────────────┐│
                             ▼│
                 ┌──────────────────────────────────┐
  ﾌｨｰﾄﾞﾊﾞｯｸ ◀── │  ③ Judge（判定）                   │
                 │  正誤判定 + 答えを漏らさない一言    │
                 └────────────┬─────────────────────┘
                              ▼
                 ┌──────────────────────────────────┐
                 │  ④ LeakGuard（漏洩ガード・非 LLM） │
                 │  生成文に答えが含まれていないか検査  │
                 └──────────────────────────────────┘
```

Diagnoser の出力のうち、Questioner に渡すのは **`focus_hints`（着目すべき箇所）だけ**であり、
`root_cause`（結論）は渡さない。Questioner は「どこを見せるべきか」は知っているが
「答えが何か」は知らない状態で質問を作る。

---

## 2. ① Diagnoser（内部診断）

セッション開始直後に 1 回だけ実行し、結果を `diagnoses` テーブルに保存する（以降は再実行しない, NFR-C3）。

### 入力

- エラーテキスト（マスキング済み）
- コード断片（任意）
- 言語 / フレームワーク（任意・未指定なら推定）
- 直前にした変更（任意）

### 出力（構造化 JSON）

```jsonc
{
  "root_cause": "props で渡される items が API 応答の遅延により初回レンダリング時 undefined になっている",
  "confidence": 0.82,
  "evidence": ["スタックトレース 3 行目が ProductList.tsx:24", "map の呼び出し元がガードされていない"],
  "focus_hints": [                 // ← Questioner に渡すのはこれだけ
    { "stage": "observe",     "look_at": "エラーメッセージの『reading map』の直前部分" },
    { "stage": "localize",    "look_at": "スタックトレース最上位のアプリケーションコード行" },
    { "stage": "hypothesize", "look_at": "map を呼んでいる変数がどこから来るか" },
    { "stage": "verify",      "look_at": "その変数の初回レンダリング時点の値" },
    { "stage": "fix",         "look_at": "非同期データが未到着の間の表示" }
  ],
  "distractor_themes": ["構文エラーの可能性", "ライブラリのバージョン不整合", "型定義の欠落"],
  "difficulty": "medium"
}
```

| フィールド | Questioner へ | 用途 |
|---|---|---|
| `root_cause` | ❌ **渡さない** | Judge の到達判定にのみ使用 |
| `evidence` | ❌ 渡さない | 到達判定の補助 |
| `confidence` | ❌ 渡さない | 低い場合は追加情報をユーザーに求める |
| `focus_hints` | ✅ 渡す | 段階ごとの「見るべき場所」 |
| `distractor_themes` | ✅ 渡す | 誤答選択肢の素材 |
| `difficulty` | ✅ 渡す | 選択肢数と質問の粒度の調整 |

### 確信度が低いとき

`confidence < 0.5` の場合、Lv1 の質問の代わりに
**情報を補う質問**（「このエラーはビルド時とブラウザ実行時のどちらで出ていますか？」）を出し、
その回答を加えて再診断する。ユーザーから見れば自然な問答であり、
実際には「AI が分からないから聞いている」のだが、それも学習として成立する。

## 3. ② Questioner（出題）

### 段階（Stage）

| Lv | Stage | 鍛える力 | 問いの型 |
|----|-------|---------|---------|
| 1 | `observe` | 観察力 | エラーメッセージを正確に読めているか |
| 2 | `localize` | 切り分け力 | 問題箇所・変更点を絞り込めるか |
| 3 | `hypothesize` | 仮説力 | 観察から原因を推論できるか |
| 4 | `verify` | 検証力 | 仮説を確かめる手段を選べるか |
| 5 | `fix` | 修正力 | 再発しない直し方を選べるか |

### 出力（構造化 JSON）

```jsonc
{
  "stage": "observe",
  "question": "このエラーメッセージは、何が undefined だったと言っていますか？",
  "options": [
    { "id": "a", "label": "map という名前の変数" },
    { "id": "b", "label": "map を呼び出そうとした対象のオブジェクト" },
    { "id": "c", "label": "map に渡したコールバック関数" },
    { "id": "d", "label": "map の戻り値" }
  ],
  "correct_option_id": "b",         // ← レスポンスには含めない
  "rationale_if_correct": "エラーの読み方として、どのオブジェクトに対する操作かを特定できている",
  "rationale_if_wrong": {
    "a": "メッセージの語順をもう一度追ってみてください",
    "c": "括弧の中と外、どちらの話をしているでしょうか",
    "d": "そもそも呼び出しは成功したでしょうか"
  }
}
```

### 出題の制約（プロンプトに明記する）

| # | 制約 |
|---|---|
| C1 | 選択肢に**修正方法**を書かない（Lv5 を除く） |
| C2 | 「〜が原因です」「〜を直せば動きます」等の断定表現を使わない |
| C3 | 具体的なファイル名・行番号を*答えとして*名指ししない（ユーザーに読ませる誘導は可） |
| C4 | 正解の選択肢だけが明らかに長い / 詳しいという形にしない（消去法で解けてしまう） |
| C5 | 誤答は `distractor_themes` から作り、**もっともらしく**する。明らかに馬鹿げた選択肢を入れない |
| C6 | 質問は 1 文。2 つのことを同時に聞かない |
| C7 | 選択肢は難易度に応じて 2〜5 個（easy=2〜3, medium=4, hard=4〜5） |

### 同段階での再出題

不正解の場合、同じ段階内で**角度を変えた**質問を最大 3 問まで出す。
3 問目も不正解ならヒントレベルを自動で 1 上げて次の質問に進む（P4: 詰まらせない）。

## 4. ③ Judge（判定）

### 4.1 選択肢の判定

正誤自体は `correct_option_id` との一致で決まる（LLM 不要）。
LLM は**フィードバック文の生成のみ**を担当する。

| 結果 | フィードバックの方針 | 例 |
|---|---|---|
| 正解 | 何が良かったかを言語化し、次の視点へ橋渡しする | 「その通り。呼び出し対象を特定できましたね。ではその値はどこで作られていますか？」 |
| 不正解 | 答えを言わず、**もう一度見るべき場所**を示す | 「惜しいです。メッセージの語順をもう一度追ってみてください」 |

### 4.2 原因宣言の到達判定（UC-04）

ユーザーの自由記述と `root_cause` を突き合わせ、次の 3 値で判定する。

| 判定 | 条件 | 挙動 |
|---|---|---|
| `reached` | 原因の本質を捉えている（表現の違いは許容） | セッション完了 → レポート生成 |
| `partial` | 症状は捉えているが原因の層が浅い（例:「undefined だから」で止まっている） | 「なぜ undefined になったのでしょう？」と 1 段深い質問に戻す |
| `not_reached` | 別の原因を挙げている | 該当段階の質問に戻す |

**重要**: `partial` / `not_reached` のフィードバックでも `root_cause` を明かさない。

## 5. ④ LeakGuard（漏洩ガード）

LLM の出力をユーザーに返す**前**に必ず通す検査。LLM を使わない決定的なルールで実装する
（`packages/core/src/leak-guard.ts`）。LLM に「漏れてないか確認して」と聞く方式は
それ自体が確率的なので採らない。

### 検出ルール

| # | ルール | 例 |
|---|---|---|
| L1 | 断定表現の検出 | 「原因は」「〜が原因です」「〜のせいで」「〜を直せば」「〜すれば解決」 |
| L2 | コードブロックの検出 | ` ``` ` を含む（Lv5 の選択肢を除き禁止） |
| L3 | 修正動詞の検出 | 「追加してください」「変更してください」「削除してください」「置き換えて」 |
| L4 | `root_cause` との語彙一致 | 診断文の特徴的な語（ストップワード除去後）が生成文に n-gram で一致 |
| L5 | 段階違反 | Lv1〜4 の出力に修正方法が含まれる |

### 検出時の挙動

1. 該当箇所を含む生成を破棄し、**制約を強めたプロンプトで 1 回だけ再生成**する
2. 再生成も検出された場合、その段階の**定型質問**（フォールバックテンプレート）にフォールバックする
3. 検出イベントは構造化ログに記録する（プロンプト改善のため）

### 回帰テスト（NFR-Q1）

代表的な 50 ケース（言語 × エラー種別）を固定データセットとして持ち、
`packages/core` のテストで漏洩検出漏れ 0 件を維持する。

## 6. ヒント設計（FR-07）

| Lv | 内容 | 例（同じ問いに対して） |
|----|------|---------------------|
| 0 | ヒントなし | — |
| 1 | 着目範囲を狭める | 「エラーメッセージの後半に注目してみてください」 |
| 2 | 見るべき対象を具体化する | 「`reading` の直後の単語が、失敗した操作を表しています」 |
| 3 | 考え方の枠組みを与える | 「`X of undefined` という形は常に『X を持っているはずの入れ物が空だった』ことを意味します」 |

**ヒント 3 でも答えは言わない。** 一般化された知識を与えるだけであり、
それを今回のケースに当てはめるのはユーザーの仕事。

### 「答えを見る」の解放条件（FR-14）

以下を**すべて**満たしたときのみボタンが解放される（具体値は Q-3 で確定）。

- 同一段階で 3 回不正解
- ヒントレベル 3 に到達済み
- セッション開始から 10 分以上経過

使用した場合、そのセッションは `scored = false` となり、スコア推移に含めない。

## 7. スコアリング（FR-09）

### 軸

5 つの段階がそのまま 5 軸になる（観察 / 切り分け / 仮説 / 検証 / 修正）。

### 段階ごとのスコア（0〜100）

```
stage_score = base(正解までに要した出題数) × hint_penalty × time_factor

  base:         1 問目で正解 = 100 / 2 問目 = 70 / 3 問目 = 40 / 未正解 = 0
  hint_penalty: ヒント Lv0 = 1.0 / Lv1 = 0.85 / Lv2 = 0.7 / Lv3 = 0.55
  time_factor:  0.9〜1.0（段階中央値の 2 倍を超えた場合に 0.9）
```

`time_factor` の影響を小さく設計しているのは、**熟考を罰しない**ため。
速さより到達を評価する（P4）。

### 総合スコア

5 軸の加重平均。重みは未決（Q-4）だが初期値は次を置く。

| 軸 | 重み | 理由 |
|---|---|---|
| 観察 | 0.15 | 前提能力 |
| 切り分け | 0.25 | 実務で最も差がつく |
| 仮説 | 0.25 | デバッグの中核 |
| 検証 | 0.20 | 思い込みを潰す力 |
| 修正 | 0.15 | 再発防止の観点 |

### 履歴表示

セッション単位のレーダーチャートと、軸ごとの推移（直近 10 セッションの移動平均）を表示する。

## 8. 振り返りレポート（FR-10）

セッション完了時に Reporter が生成する。**ここでは答えを明かしてよい**（学習が完了しているため）。

| セクション | 内容 |
|---|---|
| あなたが辿った道筋 | 各段階での選択と、正解までの試行回数 |
| つまずきポイント | 最も時間 / 試行を要した段階と、その理由の言語化 |
| 一般化された学び | 「`X of undefined` を見たら、まず X の持ち主を疑う」など**次回に転用できる形**に抽象化 |
| 次に同じ状況に出会ったら | 最初に確認すべき 3 ステップ |
| デバッグ脳スコア | 5 軸レーダーと前回比 |

**「一般化された学び」がこの製品の実質的な成果物**である。
個別のバグの答えではなく、転用可能な観点が残ることが学習の定着につながる。

## 9. モデル割り当て（NFR-C2）

| 役割 | 求められる性質 | モデル階層 | 環境変数 |
|---|---|---|---|
| Diagnoser | 推論精度。1 セッション 1 回のみなのでコストを許容 | 高性能 | `MODEL_DIAGNOSER` |
| Questioner | 速度。制約遵守。呼び出し回数が最多 | 高速・安価 | `MODEL_QUESTIONER` |
| Judge | 速度。短文生成 | 高速・安価 | `MODEL_JUDGE` |
| Reporter | 文章品質。1 セッション 1 回 | 中〜高性能 | `MODEL_DIAGNOSER` を再利用 |

具体的なモデル ID は OrcaRouter のカタログ（`GET /v1/models`）を確認して確定する（Q-1）。
すべて `provider/model` 形式（例: `openai/gpt-4o-mini`, `anthropic/claude-sonnet-4.6`）。

失敗時は `MODEL_FALLBACK` に切り替えて 1 回だけ再試行する（NFR-O1）。
