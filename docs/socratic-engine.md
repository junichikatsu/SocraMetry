本製品の中核。**「原因を分かっているのに、Gate A・B では言わない」**をどう実現するかを定義する。

## 0. 全体の流れ — 3 ゲート

```
  エラー投稿
      │
      ▼
  ┌─ Gate A ── ヒントのみ（設問なし） ─────────────┐  ★★★ 自力解決
  │  「エラーメッセージの後半に注目してみてください」   │
  └───────────────────┬───────────────────────────┘
                      │ 進まない / 利用者の要求（条件付き）
  ┌─ Gate B ─────────▼───────────────────────────┐  ★★ 誘導ありで到達
  │  選択式の設問  Lv1 観察 → Lv5 修正             │
  └───────────────────┬───────────────────────────┘
                      │ 通過しても未到達
  ┌─ Gate C ─────────▼───────────────────────────┐  ★ 開示による解決
  │  原因・根拠・修正方針・再発防止策を開示           │
  │  ＋ 振り返り 1 問（必須）                       │
  └───────────────────────────────────────────────┘
```

**答えは最後まで隠し続けるのではなく、本人が到達を試みた後に開示する。**
業務を止めないこと（P2）と、思考を促すことを両立させる設計。
どのゲートで解決したかが、そのまま評価値の主軸になる（[evaluation-model.md](evaluation-model.md)）。

以降、§1〜§5 は **Gate A・B で答えを漏らさない仕組み**を、
§6〜§8 は**各ゲートの内容と遷移**を定義する。

## 1. 設計の核心

LLM に「原因を特定して、でも答えは言わないで質問して」と 1 回で頼むと、**必ず漏れる**。
「〜が undefined になっているようですね。では…」のように、前置きで答えを言ってしまう。

そこで **役割を分離し、出題側に結論を渡さない**。

```
                 ┌──────────────────────────────────┐
  エラー入力 ───▶ │  ① Diagnoser（内部診断）           │
                 │  原因・根拠・確信度を特定する        │
                 │  出力はサーバ内部にのみ保持          │
                 └────────────┬─────────────────────┘
                              │
                    ┌─────────┴──────────┐
                    │  結論は渡さない       │  ← ここが設計の要
                    │  「着目点」だけ渡す    │
                    ▼                     
                 ┌──────────────────────────────────┐
  質問 ◀──────── │  ② Questioner（出題）              │
                 │  段階 Lv に応じた選択式の問いを作る  │
                 └──────────────────────────────────┘
                              ▲
  ユーザーの回答 ─────────────┐│
                             ▼│
                 ┌──────────────────────────────────┐
  ﾌｨｰﾄﾞﾊﾞｯｸ ◀── │  ③ Judge（判定）                   │
                 │  正誤判定 + 答えを漏らさない一言    │
                 └────────────┬─────────────────────┘
                              ▼
                 ┌──────────────────────────────────┐
                 │  ④ LeakGuard（漏洩ガード・非 LLM） │
                 │  生成文に答えが含まれていないか検査  │
                 └──────────────────────────────────┘
```

Diagnoser の出力のうち、Questioner に渡すのは **`focusHints`（着目すべき箇所）だけ**であり、
`rootCause`（結論）は渡さない。Questioner は「どこを見せるべきか」は知っているが
「答えが何か」は知らない状態で質問を作る。

## 2. ① Diagnoser（内部診断）

セッション開始**直後の別リクエスト**（`POST /sessions/:id/diagnose`）で 1 回だけ実行し、
結果を `session_secrets` テーブルに保存する（以降は再実行しない, NFR-C3）。

> **なぜ別リクエストなのか**: 診断は 10〜20 秒かかる。実行環境は Lambda ベースで
> レスポンス返却後に処理を継続できないため、サーバ側での非同期実行ができない。
> 「ユーザーが Lv1 の選択肢を読んでいる間に、クライアントから別リクエストとして撃たせる」のが
> 唯一のバックグラウンド実行手段になる（[ADR-006](architecture.md#adr-006-sse-を廃止し診断の先行実行で体感速度を確保する)）。
>
> **Lv1（観察）だけは診断なしで出題できる**ことが、この構造を成立させている。
> 「エラーメッセージは何が undefined だと言っているか」は、原因が分からなくても問える。

### 入力

- エラーテキスト（マスキング済み）
- コード断片（任意）
- 言語 / フレームワーク（任意・未指定なら推定）
- 直前にした変更（任意）

### 出力（構造化 JSON）

```jsonc
{
  "rootCause": "props で渡される items が API 応答の遅延により初回レンダリング時 undefined になっている",
  "confidence": 0.82,
  "evidence": ["スタックトレース 3 行目が ProductList.tsx:24", "map の呼び出し元がガードされていない"],
  "focusHints": [                 // ← Questioner に渡すのはこれだけ
    { "stage": "observe",     "lookAt": "エラーメッセージの『reading map』の直前部分" },
    { "stage": "localize",    "lookAt": "スタックトレース最上位のアプリケーションコード行" },
    { "stage": "hypothesize", "lookAt": "map を呼んでいる変数がどこから来るか" },
    { "stage": "verify",      "lookAt": "その変数の初回レンダリング時点の値" },
    { "stage": "fix",         "lookAt": "非同期データが未到着の間の表示" }
  ],
  "distractorThemes": ["構文エラーの可能性", "ライブラリのバージョン不整合", "型定義の欠落"],
  "difficulty": "medium"
}
```

| フィールド | Questioner へ | 用途 |
|---|---|---|
| `rootCause` | ❌ **渡さない** | Judge の到達判定にのみ使用 |
| `evidence` | ❌ 渡さない | 到達判定の補助 |
| `confidence` | ❌ 渡さない | 低い場合は追加情報をユーザーに求める |
| `focusHints` | ✅ 渡す | 段階ごとの「見るべき場所」 |
| `distractorThemes` | ✅ 渡す | 誤答選択肢の素材 |
| `difficulty` | ✅ 渡す | 選択肢数と質問の粒度の調整 |

### 確信度が低いとき

`confidence < 0.5` の場合、Lv2 の質問の代わりに
**情報を補う質問**（「このエラーはビルド時とブラウザ実行時のどちらで出ていますか？」）を出し、
その回答を加えて再診断する。ユーザーから見れば自然な問答であり、
実際には「AI が分からないから聞いている」のだが、それも学習として成立する。

### 診断が失敗したとき（NFR-O4）

`diagnosisStatus: "failed"` の場合も**問答は止めない**。
`focusHints` なしの汎用モードに切り替え、段階ごとの定型テンプレートから出題する。
体験は劣化するが、「エラーを投げたのに何も返ってこない」よりはるかにましである。

## 3. ② Questioner（出題）

### 段階（Stage）

| Lv | Stage | 鍛える力 | 問いの型 |
|----|-------|---------|---------|
| 1 | `observe` | 観察力 | エラーメッセージを正確に読めているか |
| 2 | `localize` | 切り分け力 | 問題箇所・変更点を絞り込めるか |
| 3 | `hypothesize` | 仮説力 | 観察から原因を推論できるか |
| 4 | `verify` | 検証力 | 仮説を確かめる手段を選べるか |
| 5 | `fix` | 修正力 | 再発しない直し方を選べるか |

### 出力（構造化 JSON）

```jsonc
{
  "stage": "observe",
  "question": "このエラーメッセージは、何が undefined だったと言っていますか？",
  "options": [
    { "id": "a", "label": "map という名前の変数" },
    { "id": "b", "label": "map を呼び出そうとした対象のオブジェクト" },
    { "id": "c", "label": "map に渡したコールバック関数" },
    { "id": "d", "label": "map の戻り値" }
  ],
  "correctOptionId": "b",         // ← レスポンスには含めない
  "rationaleIfCorrect": "エラーの読み方として、どのオブジェクトに対する操作かを特定できている",
  "rationaleIfWrong": {
    "a": "メッセージの語順をもう一度追ってみてください",
    "c": "括弧の中と外、どちらの話をしているでしょうか",
    "d": "そもそも呼び出しは成功したでしょうか"
  }
}
```

### 出題の制約（プロンプトに明記する）

| # | 制約 |
|---|---|
| C1 | 選択肢に**修正方法**を書かない（Lv5 を除く） |
| C2 | 「〜が原因です」「〜を直せば動きます」等の断定表現を使わない |
| C3 | 具体的なファイル名・行番号を*答えとして*名指ししない（ユーザーに読ませる誘導は可） |
| C4 | 正解の選択肢だけが明らかに長い / 詳しいという形にしない（消去法で解けてしまう） |
| C5 | 誤答は `distractorThemes` から作り、**もっともらしく**する。明らかに馬鹿げた選択肢を入れない |
| C6 | 質問は 1 文。2 つのことを同時に聞かない |
| C7 | 選択肢は難易度に応じて 2〜5 個（easy=2〜3, medium=4, hard=4〜5） |

### 同段階での再出題

不正解の場合、同じ段階内で**角度を変えた**質問を最大 3 問まで出す。
3 問目も不正解ならヒントレベルを自動で 1 上げて次の質問に進む（P4: 詰まらせない）。

## 4. ③ Judge（判定）

### 4.1 選択肢の判定

正誤自体は `correctOptionId` との一致で決まる（LLM 不要）。
LLM は**フィードバック文の生成のみ**を担当する。

| 結果 | フィードバックの方針 | 例 |
|---|---|---|
| 正解 | 何が良かったかを言語化し、次の視点へ橋渡しする | 「その通り。呼び出し対象を特定できましたね。ではその値はどこで作られていますか？」 |
| 不正解 | 答えを言わず、**もう一度見るべき場所**を示す | 「惜しいです。メッセージの語順をもう一度追ってみてください」 |

### 4.2 原因宣言の到達判定（UC-04）

ユーザーの自由記述と `rootCause` を突き合わせ、次の 3 値で判定する。

| 判定 | 条件 | 挙動 |
|---|---|---|
| `reached` | 原因の本質を捉えている（表現の違いは許容） | セッション完了 → レポート生成 |
| `partial` | 症状は捉えているが原因の層が浅い（例:「undefined だから」で止まっている） | 「なぜ undefined になったのでしょう？」と 1 段深い質問に戻す |
| `not_reached` | 別の原因を挙げている | 該当段階の質問に戻す |

**重要**: `partial` / `not_reached` のフィードバックでも `rootCause` を明かさない。

## 5. ④ LeakGuard（漏洩ガード）

LLM の出力をユーザーに返す**前**に必ず通す検査。LLM を使わない決定的なルールで実装する
（`packages/core/src/leak-guard.ts`）。LLM に「漏れてないか確認して」と聞く方式は
それ自体が確率的なので採らない。

### 検出ルール

| # | ルール | 例 |
|---|---|---|
| L1 | 断定表現の検出 | 「原因は」「〜が原因です」「〜のせいで」「〜を直せば」「〜すれば解決」 |
| L2 | コードブロックの検出 | ` ``` ` を含む（Lv5 の選択肢を除き禁止） |
| L3 | 修正動詞の検出 | 「追加してください」「変更してください」「削除してください」「置き換えて」 |
| L4 | `rootCause` との語彙一致 | 診断文の特徴的な語（ストップワード除去後）が生成文に n-gram で一致 |
| L5 | 段階違反 | Lv1〜4 の出力に修正方法が含まれる |

### 検出時の挙動

1. 該当箇所を含む生成を破棄し、**制約を強めたプロンプトで 1 回だけ再生成**する
2. 再生成も検出された場合、その段階の**定型質問**（フォールバックテンプレート）にフォールバックする
3. 検出イベントは構造化ログに記録する（プロンプト改善のため）

### 回帰テスト（NFR-Q1）

代表的な 50 ケース（言語 × エラー種別）を固定データセットとして持ち、
`packages/core` のテストで漏洩検出漏れ 0 件を維持する。

## 6. Gate A — ヒントのみの段階（FR-03）

**セッションはここから始まる。設問はまだ出さない。**
着眼点だけを示し、利用者が自力で解ける余地を最大限に残す。

| Lv | 内容 | 例（同じエラーに対して） |
|----|------|---------------------|
| 1 | 着目範囲を狭める | 「エラーメッセージの後半に注目してみてください」 |
| 2 | 見るべき対象を具体化する | 「`reading` の直後の単語が、失敗した操作を表しています」 |
| 3 | 考え方の枠組みを与える | 「`X of undefined` という形は常に『X を持っているはずの入れ物が空だった』ことを意味します」 |

**ヒント 3 でも答えは言わない。** 一般化された知識を与えるだけであり、
それを今回のケースに当てはめるのは利用者の仕事。

> **ここで解決できるのが最良の結末。** Gate A で解けた利用者は、
> 「ちょっと視点をずらせば自分で解けた」という体験を得る。
> 評価上も最上位（`gate_factor` 1.00）として扱う。

### 提示の順序

セッション開始時に Lv1 を自動提示し、Lv2 / Lv3 は利用者の要求で開放する。
**Gate A のヒントは内部診断の `focusHints` から生成できる**ため、
LLM の追加呼び出しなしで Lv1〜3 をまとめて用意できる。

## 7. ゲート遷移（FR-07）

```
  Gate A ──┬── 利用者が「解決した」→ 原因宣言 → 到達判定 → 完了（★★★）
           │
           └── 次のいずれかで Gate B へ
               ・利用者が「設問に進む」を押した
               ・ヒント Lv3 まで開放し、かつ一定時間（既定 5 分）経過

  Gate B ──┬── 原因宣言で reached → 完了（★★）
           │
           └── 次のいずれかで Gate C へ
               ・Lv5 まで通過しても原因宣言が reached にならない
               ・同一段階で 3 回不正解が 2 段階以上で発生
               ・セッション開始から一定時間（既定 30 分）経過

  Gate C ──── 原因・根拠・修正方針・再発防止策を開示 → 振り返り必須 → 完了（★）
```

具体値は未決（Q-3 / Q-4）。プロトタイプ検証後に確定する。

### 設計上の要点

| # | 要点 |
|---|---|
| 1 | **前進は常にできる。** どのゲートでも「進む」導線を塞がない（P4: 詰まらせない） |
| 2 | **後戻りはできない。** Gate B に入った後に Gate A の評価は得られない。安易に進ませないため |
| 3 | **時間経過による自動遷移を持つ。** 利用者が自分で判断できず放置するケースを救う（業務が止まる） |
| 4 | **Gate C は必ず到達可能。** 「永久に答えが得られない」状態を作らない（P2: 業務支援を最優先） |

## 8. Gate C — 開示（FR-10）

Gate B を通しても到達できなかった場合、原因を開示する。

### 開示する内容

| 項目 | 内容 |
|---|---|
| 原因 | `rootCause` をそのまま平易に説明する |
| 根拠 | `evidence`。エラーのどこからそう言えるのか |
| 修正方針 | どう直すか（コードそのものではなく方針） |
| 再発防止 | 同じミスを防ぐために何を仕込むか |

### 開示後も振り返りは必須

開示して終わりにすると、学習が成立しない。**開示直後に 1 問だけ問う。**

> 「今回、どの段階で見落としがありましたか？」
> A. エラーメッセージの読み取り
> B. 変更点の洗い出し
> C. 原因の推論
> D. 仮説の確かめ方

この回答は**スコアには使わない**（自己申告のため）が、
振り返りレポートの「つまずきポイント」の材料になり、
何より**利用者自身に自覚を促す**。

### 開示は敗北ではない

UI の文言に注意する。「答えを見る」ではなく「解説を読む」。
`gate_factor` の差も 1.00 → 0.75 と小さく設計している
（[evaluation-model.md §4.1](evaluation-model.md#41-想定される歪みと対策)）。

> **開示を罰する設計にすると、利用者は詰まったときに本製品を使わず
> 直接 AI に聞きに行く。** そうなると学習も計測も成立しない。

## 9. スコアリング

スコアの算出式・重み・公平性の設計は [evaluation-model.md](evaluation-model.md) に集約した。
本書ではエンジン側の責務のみ記す。

| 責務 | 実装 |
|---|---|
| セッション中の計測項目を記録する | `apps/function` が `sessions` アイテムに逐次追記 |
| スコアを算出する | `packages/core/src/scoring.ts`（**純関数・LLM 非依存**, NFR-Q4） |
| 難易度を保持する | 演習モードは問題集の値、実務モードは Diagnoser の `difficulty` |

**スコア算出に LLM を使わない。** 評価に使う数値が実行のたびに変わってはならないため
（[evaluation-model.md §3.4](evaluation-model.md#34-算出は再現可能でなければならないnfr-q4)）。

## 8. 振り返りレポート（FR-10）

セッション完了時に Reporter が生成する。**ここでは答えを明かしてよい**（学習が完了しているため）。

| セクション | 内容 |
|---|---|
| あなたが辿った道筋 | 各段階での選択と、正解までの試行回数 |
| つまずきポイント | 最も時間 / 試行を要した段階と、その理由の言語化 |
| 一般化された学び | 「`X of undefined` を見たら、まず X の持ち主を疑う」など**次回に転用できる形**に抽象化 |
| 次に同じ状況に出会ったら | 最初に確認すべき 3 ステップ |
| デバッグ脳スコア | 5 軸レーダーと前回比 |

**「一般化された学び」がこの製品の実質的な成果物**である。
個別のバグの答えではなく、転用可能な観点が残ることが学習の定着につながる。

## 9. モデル割り当て（NFR-C2）

| 役割 | 求められる性質 | 呼ばれるリクエスト | モデル階層 | 環境変数 |
|---|---|---|---|---|
| Diagnoser | 推論精度。1 セッション 1 回のみなのでコストを許容 | `POST /diagnose` | 高性能 | `MODEL_DIAGNOSER` |
| Questioner | 速度。制約遵守。呼び出し回数が最多 | `POST /sessions`, `POST /answers` | 高速・安価 | `MODEL_QUESTIONER` |
| Judge | 速度。短文生成 | `POST /answers`, `POST /conclusion` | 高速・安価 | `MODEL_JUDGE` |
| Reporter | 文章品質。1 セッション 1 回 | `GET /report`（初回のみ） | 中〜高性能 | `MODEL_DIAGNOSER` を再利用 |

具体的なモデル ID は OrcaRouter のカタログ（`GET /v1/models`）を確認して確定する（Q-1）。
すべて `provider/model` 形式（例: `openai/gpt-4o-mini`, `anthropic/claude-sonnet-4.6`）。

失敗時は `MODEL_FALLBACK` に切り替えて 1 回だけ再試行する（NFR-O1）。

### 1 リクエスト = 1 LLM 呼び出しの原則（NFR-C5）

LLM の待ち時間はそのまま**クラウド実行環境の実行時間**として計上され、
タイムアウトにも直結する。そのため、1 リクエスト内で LLM を直列に 2 回以上呼ばない。

| リクエスト | LLM 呼び出し | 備考 |
|---|---|---|
| `POST /answers` | Questioner **1 回のみ** | 正誤判定は `correctOptionId` との一致で決まるため LLM 不要。フィードバック文は Questioner の出力に同梱させる |
| `POST /conclusion` | Judge 1 回 | 到達判定とフィードバックを 1 回の構造化出力でまとめて得る |
| `POST /diagnose` | Diagnoser 1 回 | 最も重い。だからこそ独立したリクエストにしてある |

> **例外**: LeakGuard が漏洩を検出した場合の再生成は 2 回目の呼び出しになる。
> ここは品質のために許容し、再生成は**最大 1 回**まで。
> それでも検出された場合は LLM を呼ばずに定型テンプレートへフォールバックする（§5）。
