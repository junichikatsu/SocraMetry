## 1. 背景と課題

### 1.1 現状

生成 AI コーディングツールの普及により、エンジニアの開発速度は劇的に向上した。
一方で、学習面では次の逆流が起きている。

- エラーが出たら、そのまま AI に貼り付けて修正コードをもらう
- 動いたので次に進む。**なぜ壊れていたのか / なぜ直ったのかは分からないまま**
- 次に同種のエラーが出ても、また AI に聞くしかない

すなわち **「解決はできるが、解決能力が育たない」**。
特に初級〜中級エンジニアで、経験年数に対してデバッグ能力が伸びない層が生まれている。

### 1.2 なぜ AI では解決できないのか

現行の AI アシスタントは **答えを提示する**ことに最適化されている。
学習理論的に、答えを与えられた学習者は「認知的負荷」を経験しないため記憶に定着しない。
定着に必要なのは *想起（retrieval）* と *自力での到達（productive struggle）* である。

### 1.3 解くべき課題

> **AI を「答えを出す道具」から「問いを出す道具」に反転させ、
> デバッグという最も汎用的なエンジニアリング能力を、実務の中で鍛えられるようにする。**

## 2. プロダクトコンセプト

**【デバッグ脳育成】答えを教えない AI メンター**

- ユーザーは**実務で今まさに詰まっているエラー**を投げる（練習問題ではない）
- AI は答えを言わず、**選択式のヒント質問**を段階的に投げかける
- ユーザーは選びながら思考を整理し、**自力で原因に到達する**
- 到達までのプロセスを計測し、**デバッグ脳スコア**として可視化する

### 2.1 プロダクト原則（設計判断に迷ったらここに戻る）

| # | 原則 | 意味 |
|---|---|---|
| P1 | **答えは言わない** | 修正コード・原因の断定・ファイル名の名指しを出力しない。これを破ると製品価値がゼロになる |
| P2 | **実務のエラーを扱う** | 用意された教材ではなく、ユーザーが今困っている本物のエラーを入力とする |
| P3 | **選択式を基本とする** | 自由記述は認知負荷が高く離脱を招く。1 タップで思考が進む設計にする |
| P4 | **詰まらせない** | 詰まったらヒントを段階開放する。学習の失敗より離脱の方が有害 |
| P5 | **計測して返す** | 「できた / できなかった」で終わらせず、5 軸のスコアと振り返りを必ず返す |

### 2.2 やらないこと（Non-Goals）

- 汎用チャットアシスタント（雑談・仕様相談・コード生成）にはしない
- コードを自動修正しない。PR も作らない
- 「答えを見る」導線は用意するが、**既定の体験にはしない**

## 3. ペルソナ

### P-1 若手 Web エンジニア「佐藤」（主要ターゲット）

- 実務 1〜2 年目。AI 補完で日々コードを書いている
- エラーが出たら反射的に AI に投げる癖がついている
- 本人も「このままだとまずい」と薄々感じている
- **求めるもの**: 実務を止めずに、ついでに力がつく仕組み
- **嫌がるもの**: 遠回り。学習のために業務時間を余分に取られること

### P-2 新人研修担当「田中」

- 新人 10 名のオンボーディングを担当
- 「エラーの読み方」を教えたいが、1 対 10 では手が回らない
- **求めるもの**: 各人のつまずき傾向がデータで見えること
- ※ チーム機能は v1 スコープ外。v2 以降で対応

### P-3 独学の学習者「鈴木」

- 未経験からの転職準備中。質問できる先輩がいない
- **求めるもの**: 詰まったときに伴走してくれる存在

## 4. ユースケース

### UC-01 エラーを投げてセッションを開始する（コア）

1. ユーザーがエラーメッセージ / スタックトレース / ログを貼り付ける
2. 任意で、関連するコード断片・言語 / フレームワーク・「直前にした変更」を添える
3. システムは内部で原因を診断する（**ユーザーには一切見せない**）
4. Lv1（観察）の質問と選択肢を提示する

### UC-02 質問に答えて段階を進める（コア）

1. ユーザーが選択肢を 1 つ選ぶ
2. システムは正誤を判定し、**答えを漏らさない**フィードバックを返す
   - 正解: 「その通りです。ではその値はどこで作られていますか？」
   - 不正解: 「惜しいですね。もう一度エラーの 2 行目を読んでみてください」
3. 段階が上がり、次の質問が提示される（Lv1 → Lv5）

### UC-03 ヒントを要求する

1. 詰まったユーザーが「ヒント」を押す
2. ヒントレベルが 1 段階上がり、より直接的な誘導が出る（最大 3 段階）
3. ヒント使用回数はスコアに反映される

### UC-04 原因を宣言してセッションを完了する

1. ユーザーが「原因が分かった」を押し、自分の言葉で原因を記述する
2. システムが内部診断と突き合わせて到達判定を行う
3. 到達していれば完了、していなければ差分を踏まえた質問に戻る

### UC-05 振り返りレポートを見る

1. セッション完了時、以下を含むレポートが生成される
   - デバッグ脳スコア（5 軸）
   - どの段階でつまずいたか
   - 「次に同じ状況に出会ったら、最初に何を見るべきか」の一般化
2. レポートは履歴として保存される

### UC-06 履歴と成長を見る

1. 匿名セッション ID に紐づく過去セッション一覧を見る
2. スコアの推移と、弱い軸（例: 検証力）が分かる

### UC-07 途中で答えを見る（エスケープハッチ）

1. 一定回数以上詰まった場合のみ「答えを見る」が解放される
2. 使用した場合、そのセッションはスコア対象外となる

## 5. 機能要件

### 5.1 コア機能

| ID | 機能 | 要件 | 優先度 |
|---|---|---|---|
| FR-01 | エラー投稿 | エラーテキスト（必須, 最大 20,000 文字）、コード断片（任意）、言語 / FW（任意・自動推定）、直前の変更（任意）を受け付ける | Must |
| FR-02 | 内部診断 | LLM が原因仮説・根拠・確信度を生成し、**サーバ内部にのみ**保持する | Must |
| FR-03 | 段階的出題 | Lv1〜Lv5 の各段階について、選択式（2〜5 択）の質問を 1 問ずつ生成・提示する | Must |
| FR-04 | 回答判定 | 選択に対して正誤を判定し、答えを漏らさないソクラテス式フィードバックを返す | Must |
| FR-05 | 段階遷移 | 正解で次段階へ。不正解時は同段階内で角度を変えた再出題（同段階最大 3 問） | Must |
| FR-06 | 漏洩ガード | 生成文に原因の直接開示・修正コードが含まれていないか検査し、含む場合は再生成する | Must |
| FR-07 | ヒント開放 | ヒントレベル 1〜3 を段階的に開放する。レベル 3 でも答えは言わない | Must |
| FR-08 | 原因宣言と到達判定 | ユーザーの自由記述を内部診断と照合し、到達 / 部分到達 / 未到達を判定する | Must |
| FR-09 | スコアリング | 5 軸（観察 / 切り分け / 仮説 / 検証 / 修正）を 0〜100 で算出する | Must |
| FR-10 | 振り返りレポート | つまずき箇所・一般化された学び・次回の着眼点を生成する | Must |
| FR-11 | 匿名セッション | 認証なしで利用可能。匿名 ID（Cookie）でセッションを DB に永続化する | Must |
| FR-12 | 履歴一覧 | 匿名 ID に紐づくセッション一覧とスコア推移を表示する | Should |
| FR-13 | 秘匿情報マスキング | 入力テキストから API キー / トークン / パスワード / 絶対パス等を検出し、保存・送信前にマスクする | Must |
| FR-14 | 答えを見る | 詰まり条件を満たした場合のみ解放。使用時はスコア対象外とする | Should |
| FR-15 | ストリーミング表示 | 質問生成の待ち時間を SSE によるトークンストリームで体感短縮する | Should |
| FR-16 | モデル選択 | 用途別（診断 / 出題 / 判定）に OrcaRouter のモデルを設定で切り替えられる | Should |
| FR-17 | 認証（後付け） | 将来 GitHub OAuth を追加し、既存の匿名セッションをユーザーに引き継げる | Could（v2） |

### 5.2 スコープ外（v1 では作らない）

| 項目 | 理由 / 予定 |
|---|---|
| スクリーンショット OCR 入力 | 体験としては魅力的だが、テキスト貼り付けで価値検証は可能。v2 |
| IDE 拡張 / CLI | 体験の入口を増やす施策。コア価値の確定後に着手。v3 |
| チーム / 研修管理機能（P-2 向け） | 個人向け価値の確定が先。v2 |
| 多言語 UI（英語） | v1 は日本語のみ。v2 |
| 課金 / プラン | v1 は無料・レート制限で制御 |
| リアルタイム協調（複数人で 1 セッション） | v3 以降 |

## 6. 非機能要件

### 6.1 パフォーマンス

| ID | 要件 |
|---|---|
| NFR-P1 | エラー投稿から**最初の質問の 1 文字目が表示されるまで 5 秒以内**（SSE ストリーミング前提） |
| NFR-P2 | 回答送信から次の質問の 1 文字目まで **3 秒以内** |
| NFR-P3 | セッション完了からレポート表示まで **10 秒以内** |

> 内部診断（FR-02）は重いため、**投稿直後に非同期で開始し、Lv1 の質問生成と並行**させる。

### 6.2 セキュリティ / プライバシー

| ID | 要件 |
|---|---|
| NFR-S1 | OrcaRouter の API キーはバックエンドの環境変数にのみ保持し、フロントエンドに露出させない |
| NFR-S2 | ユーザー入力はエラーログである性質上、**認証情報が混入する前提**で扱う。保存前に自動マスキング（FR-13）を行う |
| NFR-S3 | 内部診断（原因の答え）は API レスポンスに一切含めない。DB でも `diagnoses` テーブルに分離し、公開 API から参照不可とする |
| NFR-S4 | 入力データを LLM プロバイダの学習に使わせない設定を OrcaRouter 側で確認・明記する |
| NFR-S5 | セッションデータの削除（ユーザーによる自己削除）に対応する |

### 6.3 コスト

| ID | 要件 |
|---|---|
| NFR-C1 | 1 セッションあたりの LLM 総トークン数に上限を設ける（既定: 入出力合計 80k tokens） |
| NFR-C2 | 用途別にモデルを使い分ける。診断は高性能モデル、出題・判定は安価な高速モデル |
| NFR-C3 | 内部診断結果はセッション内でキャッシュし、質問生成のたびに再診断しない |

### 6.4 可用性・運用

| ID | 要件 |
|---|---|
| NFR-O1 | LLM 呼び出し失敗時は OrcaRouter のフォールバックモデルへ自動切り替えし、それも失敗した場合はユーザーに再試行を促す |
| NFR-O2 | 全 LLM 呼び出しについて、用途 / モデル / トークン数 / レイテンシ / `X-Orca-*` ヘッダを構造化ログに残す |
| NFR-O3 | 匿名利用のため、IP ベースのレート制限（既定: 10 セッション / 時）を設ける |

### 6.5 品質

| ID | 要件 |
|---|---|
| NFR-Q1 | 漏洩ガード（FR-06）の検出漏れ率を、代表 50 ケースの回帰テストで 0 件に保つ |
| NFR-Q2 | ドメインロジック（段階遷移・スコアリング）は LLM に依存せず単体テスト可能な純関数として実装する |

## 7. 成功指標（KPI）

| 指標 | 定義 | v1 目標 |
|---|---|---|
| **自力到達率** | 「答えを見る」を使わずに原因に到達したセッションの割合 | 60% |
| セッション完走率 | 開始したセッションのうち完了したもの | 50% |
| 平均到達段階 | 離脱時点の Lv 平均 | 3.5 以上 |
| リピート率 | 2 回目以降のセッションを開始した匿名 ID の割合 | 30% |
| スコア成長 | 3 セッション以上実施したユーザーの初回→最新のスコア差 | +10 pt |

> 最重要は **自力到達率**。これが低ければ質問が難しすぎるか、ヒント設計が弱い。
> 逆に 90% を超える場合は簡単すぎ、学習効果が薄い可能性がある。

## 8. 前提と制約

| # | 内容 |
|---|---|
| A-1 | LLM へのアクセスは **OrcaRouter 経由に限定**する（必須要件） |
| A-2 | 認証は v1 では実装しないが、**後から追加できるデータモデル**とする（`sessions.user_id` を nullable で用意） |
| A-3 | v1 の UI 言語は日本語のみ |
| A-4 | 単一リージョン（日本）での提供を想定 |
