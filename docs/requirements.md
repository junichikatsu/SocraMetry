## 1. 背景と課題

### 1.1 現場で起きていること

生成 AI コーディングツールの普及により、開発速度は劇的に向上した。
一方で、**組織の人材面**では次の逆流が起きている。

- エラーが出たら、そのまま AI に貼り付けて修正コードをもらう
- 動いたので次に進む。**なぜ壊れていたのか / なぜ直ったのかは分からないまま**
- 次に同種のエラーが出ても、また AI に聞くしかない

結果として、**「解決はできるが、解決能力が育たない」**メンバーが増える。

### 1.2 これが経営・人事の問題になる理由

個人の学習意欲の問題として片付けられない理由が 3 つある。

| # | 組織側の困りごと |
|---|---|
| 1 | **メンバーの実力が見えなくなった。** AI が下駄を履かせるため、アウトプットの量と質だけでは本人の地力を測れない |
| 2 | **育成が属人化している。** 「エラーの読み方」を教えられるのは一部のシニアだけで、1 対 N ではとても手が回らない |
| 3 | **評価の根拠が主観に寄る。** 技術力の評価が、上長の印象や自己申告に依存している |

### 1.3 解くべき課題

> **AI を「答えを出す道具」から「問いを出す道具」に反転させ、
> デバッグという最も汎用的なエンジニアリング能力を、
> 業務を止めずに鍛え、かつ客観的に計測できる仕組みを、組織に提供する。**

## 2. プロダクトコンセプト

**【デバッグ脳育成】答えを教えない AI メンター**
— 業務を回しながら、実力が育ち、実力が測れる社内基盤。

### 2.1 二重の価値

SocraMetry は 1 つのプロダクトで、利用者と組織の双方に別々の価値を返す。

| 対象 | 得られるもの |
|---|---|
| **エンジニア（利用者）** | 業務のエラーが解決する。**かつ**、次から自力で解けるようになる |
| **組織（導入者）** | メンバーの**デバッグ能力が数値で可視化**され、育成と評価の根拠になる |

> **利用者にとっては業務支援ツール、組織にとっては人材可視化基盤。**
> この二重性が本製品の要点であり、「評価のためだけに使わされるツール」に
> してしまうと利用者が使わなくなるため、**業務支援としての実用性を常に優先する**。

### 2.2 AI との関わり方 — 「間接的に使う」

本製品では、利用者は **AI に直接質問できない**。

```
  ✗ 従来            利用者 ──質問──▶ AI ──答え──▶ 利用者

  ✓ SocraMetry      利用者 ──エラー──▶ AI エージェント
                                          │（内部で原因を特定するが言わない）
                    利用者 ◀──問い────────┘
                       │
                       └──思考──▶ 自力で到達
```

**AI と自由に会話するチャット欄は持たない。** 利用者ができるのは**エラーを投げること**、
**提示された選択肢を選ぶこと**、そして**原因宣言の 1 箇所でだけ自分の言葉を書くこと**である。
これは制限ではなく設計であり、「AI に聞けば済む」という逃げ道を構造的に塞ぐことが目的である。

> **自由記述を原因宣言（FR-09）だけに限る理由**: ここを選択式にすると、
> **選択肢の中に原因そのものを並べる**ことになり、P1（Gate A・B で答えを言わない）と衝突する。
> 実質 Gate C の前倒しになるため、ここだけは自由記述で受ける。
> Gate B の設問（Lv1〜5）が問うのは「原因に至る途中の一歩」なので、選択式のままでよい。
> 入力形式と判定基準は未決 Q-15。

### 2.3 3 ゲート方式 — 段階的な開示

答えは**最後まで隠し続けるのではなく、本人が到達を試みた後に開示する**。
業務を止めないことと、思考を促すことを両立させるための設計。

```
 ┌──────────────────────────────────────────────────────────────┐
 │  Gate A  ヒントのみ                                            │
 │  「エラーメッセージの後半に注目してみてください」                 │
 │  設問なし。着眼点だけを示す                                     │
 │  ここで解けたら ★★★  自力解決                                  │
 └────────────────────────┬─────────────────────────────────────┘
                          │ 進まない / 一定時間経過（条件付き）
 ┌────────────────────────▼─────────────────────────────────────┐
 │  Gate B  選択式の設問（Lv1 観察 → Lv5 修正）                    │
 │  「このエラーは何が undefined だと言っていますか？ A/B/C/D」      │
 │  段階的に核心へ近づける                                         │
 │  ここで解けたら ★★   誘導ありで到達                             │
 └────────────────────────┬─────────────────────────────────────┘
                          │ 設問を通しても到達できない
 ┌────────────────────────▼─────────────────────────────────────┐
 │  Gate C  正解の開示 + 解説                                     │
 │  原因・根拠・修正方針・再発防止策を提示する                       │
 │  ここまで来たら ★     開示による解決（それでも学習は成立する）     │
 └──────────────────────────────────────────────────────────────┘
```

**どのゲートで解決したかは、評価の重要な内訳のひとつとして記録する。**
ただし**評価値の主軸には置かない。** 主軸は v0.1 では **5 軸スコア**、v0.2 以降は**成長率**とし、
到達ゲートは NFR-F5 が求める「内訳と根拠」の一項目として併記する。
学習体験の設計と評価指標の設計が、ここで一本の線につながっている。

> **到達ゲートを主軸に置かない理由**: 主軸にすると Gate C が構造的に最低評価になり、
> NFR-F4「開示の利用を減点の主因にしない」と両立しなくなる。
> 算出式でも到達ゲートは補正係数（`gate_factor` A=1.00 / B=0.90 / C=0.75）として扱っており、
> 主軸は成長率である（[evaluation-model.md §3.2 / §4.2](evaluation-model.md#32-セッションスコア)）。

> **Gate C を用意する理由**: 業務支援である以上、メンバーを永久に詰まらせるわけにいかない。
> 「答えを見た」ことを罰する設計にすると、**利用者はツールを使わずに
> 直接 AI に聞きに行く**（＝製品が使われなくなる）。
> Gate C は敗北ではなく、正しい着地点のひとつとして扱う。
> 詳細は [evaluation-model.md](evaluation-model.md)。

### 2.4 2 つの利用モード

| モード | 入力 | 目的 | 評価での役割 |
|---|---|---|---|
| **実務モード** (`live`) | 利用者自身が遭遇したエラー | 業務支援。今困っていることを解決する | **取り組み量**と傾向を見る。問題が人によって違うため、点数の横比較には使わない |
| **演習モード** (`assessment`) | 組織が割り当てた共通問題 | 育成・評価。同じ問題を複数人が解く | **横比較の主軸**。同一条件のため、評価値として成立する |

> **この分離が評価の妥当性を担保する。** 実務モードのエラーは難易度も文脈もバラバラなので、
> そのスコアで人を並べると不公平になる。同一問題を解く演習モードを別に用意し、
> **比較は演習モードで、成長の観察は実務モードで**行う。

### 2.5 社内ナレッジの循環

実務モードで起きた問答は、匿名化・汎用化のうえ**社内の問題集**に蓄積できる。

```
  実際に起きたエラー ──▶ 問答セッション ──▶ 匿名化・汎用化
                                              │
       新メンバーの演習問題 ◀── 社内問題集 ◀──┘
```

「うちの現場で実際に起きたエラー」が、そのまま「うちの新人が解くべき問題」になる。
外部の汎用教材では扱えない、**その組織固有のつまずきどころ**が資産化される。

### 2.6 プロダクト原則（設計判断に迷ったらここに戻る）

| # | 原則 | 意味 |
|---|---|---|
| P1 | **Gate A・B では答えを言わない** | 修正コード・原因の断定・ファイル名の名指しを出力しない。開示は Gate C でのみ行う |
| P2 | **業務支援を最優先する** | 学習効果と業務の停止が衝突したら、業務を優先して開示する。使われない仕組みは評価にも使えない |
| P3 | **選択式を基本とする** | 自由記述は認知負荷が高く離脱を招く。1 タップで思考が進む設計にする。**例外は原因宣言（FR-09）のみ**（→ §2.2） |
| P4 | **AI と直接会話させない** | チャット欄を作らない。逃げ道を構造的に塞ぐ |
| P5 | **計測して返す** | 「できた / できなかった」で終わらせず、個人には成長を、組織には傾向を返す |
| P6 | **評価は人を裁く道具にしない** | 順位付けは可能にするが、既定は「成長の可視化」。詳細は [evaluation-model.md](evaluation-model.md) |

### 2.7 なぜ AI でなければ成立しないのか

**ルールベースで代替できない部分がどこかを明確にしておく。**
AI を使うこと自体が目的ではないため、使う場所と使わない場所を意識的に分ける。

#### AI でなければできないこと

| # | 処理 | ルールベースで代替できない理由 |
|---|---|---|
| 1 | **エラーから原因を推定する** | エラーメッセージの種類は事実上無限にある。正規表現の辞書では、未知のエラー・複数原因の組み合わせ・そのプロジェクト固有の文脈に対応できない |
| 2 | **「今この人がどこを見落としているか」に合わせて問いを作る** | 同じエラーでも、直前の変更・使っているフレームワーク・これまでの回答によって、次に問うべきことが変わる。**問いの個別化**であり、テンプレートの選択では成立しない |
| 3 | **もっともらしい誤答選択肢を作る** | 誤答が明らかに馬鹿げていると、消去法で解けてしまい学習にならない。**その文脈でありえた誤解**を生成する必要がある |
| 4 | **自由記述の原因宣言が、本質を捉えているか判定する** | 表現は人によって違う。「items が空だった」「APIが返る前に描画された」は同じことを指しうる。文字列一致では判定できない |

> **中核は 2 番目。** 本製品の価値は「答えを隠すこと」ではなく
> **「その人に効く問いを、その場で作ること」**にある。
> 固定の問題集を出すだけなら AI は要らない。実務で今起きているエラーに対して、
> 段階に応じた問いをその場で生成するからこそ、業務支援として成立する。

#### あえて AI を使わないこと

| 処理 | 実装 | 理由 |
|---|---|---|
| **答えが漏れていないかの検査**（LeakGuard） | 決定的な正規表現ルール | LLM に「漏れてないか確認して」と聞く方式は、**検査自体が確率的**になる。ここは確実性が要る |
| **秘匿情報のマスキング** | 決定的な正規表現 | LLM に送る**前**に処理する必要があるため、そもそも LLM を使えない |
| **スコアの算出** | 純関数 | 評価に使う数値が実行のたびに変わってはならない（NFR-Q4） |
| **選択肢の正誤判定** | 保存した正解との一致 | LLM に判定させる理由がない。安く・速く・確実 |

> **「AI を使う場所」と「使ってはいけない場所」を分けていることが、この設計の要点である。**
> 全部を AI に任せると、答えが漏れ、スコアが揺れ、コストが膨らむ。

### 2.8 やらないこと（Non-Goals）

- 汎用チャットアシスタント（雑談・仕様相談・コード生成）にはしない
- コードを自動修正しない。PR も作らない
- **スコアを人事システムへ自動連携しない。** レポートを出力するところまでが本製品の責務

## 3. ペルソナ

BtoB のため、**買う人・使う人・見る人**を分けて定義する。

### P-1 エンジニアリングマネージャー / 技術部門長「田中」（**導入決定者**）

- メンバー 15 名を統括。半期ごとに技術評価を行う立場
- **困っていること**: AI 前提の開発になり、アウトプットから本人の地力が読めない。
  評価の根拠が「印象」と「自己申告」になっている
- **求めるもの**: メンバーの技術力を、継続的・客観的に把握できるデータ
- **懸念**: 「監視ツール」と受け取られてメンバーの反発を招くこと
- **成功の定義**: 評価面談で、具体的な根拠を持って育成方針を語れる

### P-2 若手エンジニア「佐藤」（**主要利用者**）

- 実務 1〜2 年目。AI 補完で日々コードを書いている
- エラーが出たら反射的に AI に投げる癖がついている。本人も薄々まずいと感じている
- **求めるもの**: 業務を止めずに、ついでに力がつくこと
- **嫌がるもの**: 遠回り。学習のために業務時間を余分に取られること。**評価されている感覚**
- **成功の定義**: 今日のエラーが解決し、来月は同種のエラーを自力で解ける

### P-3 育成担当 / テックリード「鈴木」（**運用者**）

- 新人 10 名のオンボーディングを担当
- 「エラーの読み方」を教えたいが、1 対 10 では手が回らない
- **求めるもの**: 自分の代わりに問いかけてくれる存在と、各人のつまずき傾向のデータ
- **成功の定義**: 誰にどこを重点的に教えるべきかが、勘ではなくデータで分かる

### P-4 人事担当「山田」（**閲覧者**）

- 技術の中身は分からないが、評価制度の運用責任を持つ
- **求めるもの**: 技術力を、他職種と同じ土俵で語れる形（5 軸・成長率）にした指標
- **嫌がるもの**: 説明できない数値。ブラックボックスなスコア

> **P-2 が使い続けてくれなければ、P-1 が欲しいデータは 1 行も溜まらない。**
> 導入決定者は P-1 だが、**プロダクトの設計優先度は P-2 を上に置く。**

## 4. ユースケース

### 4.1 実務モード（利用者）

#### UC-01 エラーを投げてセッションを開始する（コア）

1. 利用者がエラーメッセージ / スタックトレース / ログを貼り付ける
2. 任意で、関連するコード断片・言語 / FW・「直前にした変更」を添える
3. システムは内部で原因を診断する（**利用者には一切見せない**）
4. **Gate A**: 着眼点のヒントのみを提示する（設問はまだ出ない）

#### UC-02 ヒントだけで自力解決する（最良の結末）

1. 利用者は Gate A のヒントを見て、自分で調べて解決する
2. 「解決した」を押し、原因を自分の言葉で記述する
3. 到達判定を受け、**自力解決**として記録される

#### UC-03 設問に答えて段階を進める（Gate B）

1. Gate A で進まない場合（一定時間経過 or 利用者が「設問に進む」を押す）、Gate B に入る
2. Lv1（観察）から順に、選択式の設問が 1 問ずつ提示される
3. 正誤に応じて、**答えを漏らさない**フィードバックが返る
4. 段階が上がる（Lv1 → Lv5）

#### UC-04 原因を宣言してセッションを完了する

1. 利用者が「原因が分かった」を押し、自分の言葉で原因を記述する
2. システムが内部診断と突き合わせて到達判定を行う
3. 到達していれば完了、していなければ差分を踏まえた設問に戻る

#### UC-05 答えの開示を受ける（Gate C）

1. Gate B を通しても到達できない場合、開示が解放される
2. 原因・根拠・修正方針・再発防止策が提示される
3. **開示後も振り返りは必ず実施する。** 「どこで見落としたか」を言語化させる

#### UC-06 振り返りレポートを見る

1. セッション完了時、以下が生成される
   - デバッグ脳スコア（5 軸）と到達ゲート
   - どの段階でつまずいたか
   - **一般化された学び**（次に転用できる形）
2. レポートは履歴として保存される

#### UC-07 自分の成長を見る（個人ダッシュボード）

1. 到達ゲートの分布、5 軸スコアの推移、学習時間、正答率を見る
2. **自分のデータは常に自分が見られる**（P6 の前提）

### 4.2 演習モード（利用者 + 運用者）

#### UC-08 割り当てられた問題を解く

1. 運用者から問題（または問題セット）が割り当てられ、通知される
2. 利用者は実務モードと同じ 3 ゲートの体験で解く
3. 結果は**同一条件で他メンバーと比較可能**な形で記録される

#### UC-09 問題を割り当てる（運用者）

1. 運用者が社内問題集から問題セットを選ぶ
2. 対象メンバー（個人 / チーム全員 / 新入社員グループ）と期限を指定する
3. 進捗と結果を一覧で追える

#### UC-10 実務セッションを問題集に登録する（運用者）

1. 完了した実務セッションのうち、教材価値の高いものを選ぶ
2. **匿名化・汎用化**（社名・パス・固有名詞の除去）を行い、問題集に登録する
3. 難易度・カテゴリ・対象レベルのタグを付ける

### 4.3 組織（管理者・閲覧者）

#### UC-11 組織ダッシュボードを見る

1. 管理者がメンバー横断の状況を見る
   - 取り組み時間・セッション数
   - 到達ゲートの分布（自力解決率）
   - 正答率、正解までの平均所要時間
   - 5 軸のチーム平均と個人分布
2. 弱い軸が組織全体の傾向として見える（例:「検証力が全体的に低い」）

#### UC-12 ランキングを見る

1. 演習モードの共通問題について、順位を表示する
2. **既定は「チーム内・任意参加・期間限定」**。全社常時ランキングは管理者が明示的に有効化した場合のみ

#### UC-13 評価レポートを出力する（人事評価用）

1. 管理者が対象メンバーと期間を指定する
2. 5 軸スコア、成長率、到達ゲート分布、取り組み量を含む**説明可能なレポート**を出力する
3. **単一の総合点だけを出す形にはしない。** 根拠となる内訳を必ず併記する

>
> **FR-16 / FR-17 を新設した。** どちらも v0.1 の実装対象でありながら
> 要件として明文化されていなかった（[scope-v0.1.md](scope-v0.1.md) の F04 / F12 に相当）。
>
> **FR-11 の適用範囲を明記した。** マスキングは **LLM に送る前**の処理であるため
> LLM を使えず、決定的な正規表現に限られる（§2.7）。
> **顧客名・サービス名のような固有名詞は正規表現では検出できない**ため、v0.1 では
> 「形式が決まったもの + 除外語リスト」に絞り、それ以外は**送信前プレビューで利用者が伏せる**形で担保する。
> 組織単位の辞書による自動化は **FR-41（v0.2）**。
> §2.5 / UC-10 の匿名化は**保存後の二次処理**で LLM を使えるため、別要件（FR-35）として扱う。
>
> **対象は「利用者が入力するすべてのテキスト」である。** 原因宣言（FR-09）は Judge に、
> 振り返りの回答は Reporter に送られるため、ここを通さないと素通りする。
> **どの入力が LLM に届くかで判断し、画面ごとに例外を作らない。**
>
> **絶対パスはプレフィックス全体を伏せる**（`/Users/tanaka/projects/acme/src/a.js:42` →
> `<path>/a.js:42`）。ユーザー名部だけを伏せる方式では、**中間ディレクトリに含まれる
> 顧客名・プロジェクト名が残る**ため。診断に効くのはエラーメッセージ・ファイル名・行番号であり、
> ディレクトリ階層ではないので、**強く伏せても診断精度は落ちない**
> （[security.md §3](security.md#3-秘匿情報のマスキングr1-への対策) 実装原則 #4）。
>
> **マスク結果の表示は 2 段階に分かれる。**
>
> | | 内容 | v0.1 |
> |---|---|---|
> | A | 貼り付けた瞬間に、マスク後のテキストを入力欄の下のパネルに出す | **必須** |
> | B | 利用者が選択範囲を指定して追加で伏せる | 実装予定（Day 4 に最終判断） |
>
> **A は確認画面（モーダル）ではなく常時表示のパネルとする。** 追加のクリックが発生すると
> デモの尺と NFR-P1 に影響するため。**プレビューを出すのはエラー投稿画面のみ**とし、
> 原因宣言には出さない（自分の言葉で書くため混入リスクが構造的に低い）。
> **マスキング自体はすべての入力に適用する。**
>
> **FR-07 の文面を具体化した。** 従来の「一定時間経過または利用者の要求」では、
> **明示要求で即座に進めること**が読み取れなかった。
> あわせて「待ち時間は設定で変更できる」「入力中は時間条件を適用しない」を明記した。

### 6.1 パフォーマンス

レスポンスはバッファされるため（[E1](architecture.md#2-enebular-採用にともなう-4-つの制約)）、
「1 文字目まで」ではなく**レスポンス全体の完了時間**で規定する。

> **計測条件**: NFR-P1〜P3 は**本番相当のテザリング回線**で計測する。
> レスポンスがバッファされて**全文が一度に返る**ため、回線が細いと体感が一段悪化する。
> 会場 Wi-Fi 前提の数字とテザリング前提の数字は別物になるので、条件を固定する。
> 計測の起点は**利用者が送信ボタンを押した時点**とし、送信前のマスク確認（FR-11）は含めない。

| ID | 要件 |
|---|---|
| NFR-P1 | エラー投稿から **Gate A のヒントが表示されるまで 5 秒以内**。内部診断はこの経路に含めない（FR-13） |
| NFR-P2 | 回答送信から次の設問が表示されるまで **4 秒以内** |
| NFR-P3 | セッション完了からレポート表示まで **10 秒以内**（初回生成時） |
| NFR-P4 | 組織ダッシュボードの表示は **3 秒以内**。集計はセッション完了時に事前計算する |
| NFR-P5 | すべてのリクエストは実行環境のタイムアウト内に収める。1 リクエストで LLM を 2 回以上直列に呼ばない。ただし **FR-08 の LeakGuard による再生成は 1 回のみ許容する** |

### 6.2 セキュリティ / プライバシー

BtoB では、**業務コードとエラーログという機微な資産**を預かる。要求水準が上がる。

| ID | 要件 |
|---|---|
| NFR-S1 | OrcaRouter の API キーはクラウド実行環境の環境変数にのみ保持し、FE とリポジトリに露出させない |
| NFR-S2 | 利用者入力は**認証情報が混入する前提**で扱う。保存前・LLM 送信前に自動マスキング（FR-11） |
| NFR-S3 | 内部診断と各設問の正解は Gate C 到達前の API レスポンスに含めない。データストア上も別テーブルに隔離する |
| NFR-S4 | 入力データを LLM プロバイダの学習に使わせない設定を OrcaRouter 側で確認・明記する |
| NFR-S5 | **テナント分離**: すべてのデータアクセスに組織 ID を含め、他組織のデータを参照できないことをリポジトリ層で強制する |
| NFR-S6 | **ロールに応じた閲覧制御**: `member` は自分のデータのみ。`lead` は自チーム。`admin` は組織全体 |
| NFR-S7 | データ削除に対応する（個人セッション / 退職者データ / 組織全体） |
| NFR-S8 | フロントと API を別オリジンに置く場合、CORS は `ALLOWED_ORIGIN` の完全一致で許可する（v0.1 は同一オリジン配信のため該当しない） |
| NFR-S9 | **監査ログ**: 誰が誰の評価データを閲覧したかを記録する（P6 の担保） |

### 6.3 公平性・説明可能性 ★評価に使うため必須

| ID | 要件 |
|---|---|
| NFR-F1 | **スコアの算出根拠を利用者本人が確認できる。** ブラックボックスな数値を人事評価に使わない |
| NFR-F2 | 横比較に使ってよいのは**演習モード（同一問題）のみ**。実務モードのスコアで順位付けしない |
| NFR-F3 | 難易度による正規化を行う（FR-25）。難しい問題に挑んだ人が不利にならない |
| NFR-F4 | **Gate C（開示）の利用を減点の主因にしない。** 詰まったときに開示を避ける動機を作らない |
| NFR-F5 | 評価レポートは単一の総合点だけを出さず、必ず内訳と根拠を併記する |
| NFR-F6 | 利用者は自分のデータを常に閲覧でき、事実誤認があれば異議を申し立てられる導線を持つ |

> **根拠**: 指標が評価に使われた瞬間、指標は歪む（Goodhart の法則）。
> 対策を設計に埋め込まないと、「簡単なエラーだけ投げる」「詰まっても開示を使わず放置する」
> といった行動を誘発し、**業務支援としての価値まで壊れる**。
> 詳細は [evaluation-model.md](evaluation-model.md)。

## 7. 成功指標（KPI）

### 7.1 v0.1 — 体験が成立しているか

**v0.1 の目的は「問いによって自力到達できる」ことの検証であり、
利用者数や継続率ではない。** 少数の実利用で以下を測る。

| 指標 | 定義 | 目標 | 測り方 |
|---|---|---|---|
| **自力解決率** | **完了セッションのうち** Gate A または B で解決した割合 | 50% 以上 | セッションの `reachedGate` |
| Gate A 解決率 | **完了セッションのうち**ヒントのみで解決した割合 | 15% 以上 | 同上 |
| セッション完走率 | 開始したセッションのうち完了したもの | 60% 以上 | `status === "completed"` |
| **未完了率** | 開始したセッションのうち完了しなかった割合。**離脱とツール外解決を区別できない**ため単独で見る | — | `status !== "completed"` |
| **答えの漏洩** | Gate A・B の生成文に答えが含まれた件数 | **0 件** | LeakGuard の検出ログ + 目視 |
| 初回応答時間 | エラー投稿から Gate A 表示まで | 5 秒以内 | サーバログ |
| **1 セッション単価** | LLM の実測コスト | 10 円以下 | 単価ログ（FR-28） |

> **最重要は自力解決率と漏洩 0 件。**
> 自力解決率が低ければ Gate A のヒント設計かゲート遷移条件が弱い。
> 逆に 90% を超える場合は簡単すぎ、学習効果も評価の分解能も薄い。
> 漏洩は 1 件でも起きれば製品価値が消えるため、目標は 0 件しかありえない。

> **自力解決率の分母を「完了セッション」に限る理由**:
> ヒントだけで解決してツールに戻らなかった人（UC-02 = 最良の結末）は未完了として残る。
> 開始セッション全体を分母にすると、**最もうまくいったケースだけが分母から消え、
> 自力解決率が構造的に過小評価される**。バイアスが一方向にかかるため、指標として成立しない。
> 「離脱」と「ツール外で解決」は v0.1 では区別できないので、**未完了率は混ぜずに並記する。**
> 次回ログイン時に前回の結末を 1 問だけ聞いて拾う導線は v0.2 で検討する。

### 7.2 v0.2 以降 — 利用者側（これが崩れると何も溜まらない）

| 指標 | 定義 | 目標 |

| セッション完走率 | 開始したセッションのうち完了したもの | 60% |

>

## 10. ビジネス成立性

### 10.1 一言で言うと

> **エラーを「解決してもらう場所」から「解決できるようになる場所」に変えるサービス。**

### 10.2 誰が誰にいくらで

| 項目 | 内容 |
|---|---|
| **売る相手** | エンジニア組織を持つ企業。**決裁者はエンジニアリングマネージャー / 技術部門長**（P-1） |
| **使う人** | 若手〜中堅エンジニア（P-2）、育成担当（P-3） |
| **課金モデル** | **月額サブスクリプション / 利用者 1 人あたり** |
| **想定価格帯** | 1 人あたり 月額 1,000〜2,000 円（要検証） |
| **原価** | LLM コストは**1 人あたり月 50 円程度**（[cost-model.md §5.3](cost-model.md#53-規模別の月額試算)）。粗利率は高い |

### 10.3 なぜ買うのか

導入企業が払う理由は 2 つあり、**どちらも既存の予算から出る**。

| # | 買う理由 | 既存の代替手段とその限界 |
|---|---|---|
| 1 | **育成コストの削減** | シニアが 1 対 1 で教える。人件費が高く、スケールしない |
| 2 | **技術力評価の客観化** | 上長の主観と自己申告。AI が下駄を履かせるため、成果物から地力が読めなくなった |

> **新規の予算を取りに行かない。** 研修予算と評価制度の運用コストという、
> **既に存在する支出**の置き換えとして提案できることが、導入のしやすさにつながる。

### 10.4 既存サービスとの違い

| 分類 | 例 | 違い |
|---|---|---|
| AI コーディング支援 | 各種 AI アシスタント | **答えを出すのが目的**。使うほど本人の力は育たない |
| プログラミング学習 | オンライン学習サービス | **教材が固定**。実務で今起きているエラーは扱えない |
| 技術力測定 | コーディングテスト | **試験の場が別**。年数回の単発で、日常業務とつながらない |

**本製品の位置**: 実務のエラーをそのまま入力にして、
**業務を進めながら**育成と測定が同時に起きる。学習の場と実務の場が分かれていない。

### 10.5 成長の道筋

```
 v0.1  個人利用で体験を検証       → 「問いで自力到達できる」ことを示す
 v0.2  組織機能・演習・問題集     → 横比較が成立し、評価に使える
 v0.3  社内問題集の蓄積           → その企業固有の教材が資産化され、乗り換えコストが上がる
```

**v0.3 の社内問題集が参入障壁になる。** 使い続けるほど、
その組織で実際に起きたエラーが教材として溜まる。これは他社製品に持ち出せない。
