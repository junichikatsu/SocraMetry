## 1. 背景と課題

### 1.1 現場で起きていること

生成 AI コーディングツールの普及により、開発速度は劇的に向上した。
一方で、**組織の人材面**では次の逆流が起きている。

- エラーが出たら、そのまま AI に貼り付けて修正コードをもらう
- 動いたので次に進む。**なぜ壊れていたのか / なぜ直ったのかは分からないまま**
- 次に同種のエラーが出ても、また AI に聞くしかない

結果として、**「解決はできるが、解決能力が育たない」**メンバーが増える。

### 1.2 これが経営・人事の問題になる理由

個人の学習意欲の問題として片付けられない理由が 3 つある。

| # | 組織側の困りごと |
|---|---|
| 1 | **メンバーの実力が見えなくなった。** AI が下駄を履かせるため、アウトプットの量と質だけでは本人の地力を測れない |
| 2 | **育成が属人化している。** 「エラーの読み方」を教えられるのは一部のシニアだけで、1 対 N ではとても手が回らない |
| 3 | **評価の根拠が主観に寄る。** 技術力の評価が、上長の印象や自己申告に依存している |

### 1.3 解くべき課題

> **AI を「答えを出す道具」から「問いを出す道具」に反転させ、
> デバッグという最も汎用的なエンジニアリング能力を、
> 業務を止めずに鍛え、かつ客観的に計測できる仕組みを、組織に提供する。**

## 2. プロダクトコンセプト

**【デバッグ脳育成】答えを教えない AI メンター**
— 業務を回しながら、実力が育ち、実力が測れる社内基盤。

### 2.1 二重の価値

SocraMetry は 1 つのプロダクトで、利用者と組織の双方に別々の価値を返す。

| 対象 | 得られるもの |
|---|---|
| **エンジニア（利用者）** | 業務のエラーが解決する。**かつ**、次から自力で解けるようになる |
| **組織（導入者）** | メンバーの**デバッグ能力が数値で可視化**され、育成と評価の根拠になる |

> **利用者にとっては業務支援ツール、組織にとっては人材可視化基盤。**
> この二重性が本製品の要点であり、「評価のためだけに使わされるツール」に
> してしまうと利用者が使わなくなるため、**業務支援としての実用性を常に優先する**。

### 2.2 AI との関わり方 — 「間接的に使う」

本製品では、利用者は **AI に直接質問できない**。

```
  ✗ 従来            利用者 ──質問──▶ AI ──答え──▶ 利用者

  ✓ SocraMetry      利用者 ──エラー──▶ AI エージェント
                                          │（内部で原因を特定するが言わない）
                    利用者 ◀──問い────────┘
                       │
                       └──思考──▶ 自力で到達
```

チャット欄はなく、利用者ができるのは**エラーを投げること**と
**提示された選択肢を選ぶこと**だけ。これは制限ではなく設計であり、
「AI に聞けば済む」という逃げ道を構造的に塞ぐことが目的である。

### 2.3 3 ゲート方式 — 段階的な開示

答えは**最後まで隠し続けるのではなく、本人が到達を試みた後に開示する**。
業務を止めないことと、思考を促すことを両立させるための設計。

```
 ┌──────────────────────────────────────────────────────────────┐
 │  Gate A  ヒントのみ                                            │
 │  「エラーメッセージの後半に注目してみてください」                 │
 │  設問なし。着眼点だけを示す                                     │
 │  ここで解けたら ★★★  自力解決                                  │
 └────────────────────────┬─────────────────────────────────────┘
                          │ 進まない / 一定時間経過（条件付き）
 ┌────────────────────────▼─────────────────────────────────────┐
 │  Gate B  選択式の設問（Lv1 観察 → Lv5 修正）                    │
 │  「このエラーは何が undefined だと言っていますか？ A/B/C/D」      │
 │  段階的に核心へ近づける                                         │
 │  ここで解けたら ★★   誘導ありで到達                             │
 └────────────────────────┬─────────────────────────────────────┘
                          │ 設問を通しても到達できない
 ┌────────────────────────▼─────────────────────────────────────┐
 │  Gate C  正解の開示 + 解説                                     │
 │  原因・根拠・修正方針・再発防止策を提示する                       │
 │  ここまで来たら ★     開示による解決（それでも学習は成立する）     │
 └──────────────────────────────────────────────────────────────┘
```

**どのゲートで解決したかが、そのまま評価値の主軸になる。**
学習体験の設計と評価指標の設計が、ここで一本の線につながっている。

> **Gate C を用意する理由**: 業務支援である以上、メンバーを永久に詰まらせるわけにいかない。
> 「答えを見た」ことを罰する設計にすると、**利用者はツールを使わずに
> 直接 AI に聞きに行く**（＝製品が使われなくなる）。
> Gate C は敗北ではなく、正しい着地点のひとつとして扱う。
> 詳細は [evaluation-model.md](evaluation-model.md)。

### 2.4 2 つの利用モード

| モード | 入力 | 目的 | 評価での役割 |
|---|---|---|---|
| **実務モード** (`live`) | 利用者自身が遭遇したエラー | 業務支援。今困っていることを解決する | **取り組み量**と傾向を見る。問題が人によって違うため、点数の横比較には使わない |
| **演習モード** (`assessment`) | 組織が割り当てた共通問題 | 育成・評価。同じ問題を複数人が解く | **横比較の主軸**。同一条件のため、評価値として成立する |

> **この分離が評価の妥当性を担保する。** 実務モードのエラーは難易度も文脈もバラバラなので、
> そのスコアで人を並べると不公平になる。同一問題を解く演習モードを別に用意し、
> **比較は演習モードで、成長の観察は実務モードで**行う。

### 2.5 社内ナレッジの循環

実務モードで起きた問答は、匿名化・汎用化のうえ**社内の問題集**に蓄積できる。

```
  実際に起きたエラー ──▶ 問答セッション ──▶ 匿名化・汎用化
                                              │
       新メンバーの演習問題 ◀── 社内問題集 ◀──┘
```

「うちの現場で実際に起きたエラー」が、そのまま「うちの新人が解くべき問題」になる。
外部の汎用教材では扱えない、**その組織固有のつまずきどころ**が資産化される。

### 2.6 プロダクト原則（設計判断に迷ったらここに戻る）

| # | 原則 | 意味 |
|---|---|---|
| P1 | **Gate A・B では答えを言わない** | 修正コード・原因の断定・ファイル名の名指しを出力しない。開示は Gate C でのみ行う |
| P2 | **業務支援を最優先する** | 学習効果と業務の停止が衝突したら、業務を優先して開示する。使われない仕組みは評価にも使えない |
| P3 | **選択式を基本とする** | 自由記述は認知負荷が高く離脱を招く。1 タップで思考が進む設計にする |
| P4 | **AI と直接会話させない** | チャット欄を作らない。逃げ道を構造的に塞ぐ |
| P5 | **計測して返す** | 「できた / できなかった」で終わらせず、個人には成長を、組織には傾向を返す |
| P6 | **評価は人を裁く道具にしない** | 順位付けは可能にするが、既定は「成長の可視化」。詳細は [evaluation-model.md](evaluation-model.md) |

### 2.7 やらないこと（Non-Goals）

- 汎用チャットアシスタント（雑談・仕様相談・コード生成）にはしない
- コードを自動修正しない。PR も作らない
- **スコアを人事システムへ自動連携しない。** レポートを出力するところまでが本製品の責務

## 3. ペルソナ

BtoB のため、**買う人・使う人・見る人**を分けて定義する。

### P-1 エンジニアリングマネージャー / 技術部門長「田中」（**導入決定者**）

- メンバー 15 名を統括。半期ごとに技術評価を行う立場
- **困っていること**: AI 前提の開発になり、アウトプットから本人の地力が読めない。
  評価の根拠が「印象」と「自己申告」になっている
- **求めるもの**: メンバーの技術力を、継続的・客観的に把握できるデータ
- **懸念**: 「監視ツール」と受け取られてメンバーの反発を招くこと
- **成功の定義**: 評価面談で、具体的な根拠を持って育成方針を語れる

### P-2 若手エンジニア「佐藤」（**主要利用者**）

- 実務 1〜2 年目。AI 補完で日々コードを書いている
- エラーが出たら反射的に AI に投げる癖がついている。本人も薄々まずいと感じている
- **求めるもの**: 業務を止めずに、ついでに力がつくこと
- **嫌がるもの**: 遠回り。学習のために業務時間を余分に取られること。**評価されている感覚**
- **成功の定義**: 今日のエラーが解決し、来月は同種のエラーを自力で解ける

### P-3 育成担当 / テックリード「鈴木」（**運用者**）

- 新人 10 名のオンボーディングを担当
- 「エラーの読み方」を教えたいが、1 対 10 では手が回らない
- **求めるもの**: 自分の代わりに問いかけてくれる存在と、各人のつまずき傾向のデータ
- **成功の定義**: 誰にどこを重点的に教えるべきかが、勘ではなくデータで分かる

### P-4 人事担当「山田」（**閲覧者**）

- 技術の中身は分からないが、評価制度の運用責任を持つ
- **求めるもの**: 技術力を、他職種と同じ土俵で語れる形（5 軸・成長率）にした指標
- **嫌がるもの**: 説明できない数値。ブラックボックスなスコア

> **P-2 が使い続けてくれなければ、P-1 が欲しいデータは 1 行も溜まらない。**
> 導入決定者は P-1 だが、**プロダクトの設計優先度は P-2 を上に置く。**

## 4. ユースケース

### 4.1 実務モード（利用者）

#### UC-01 エラーを投げてセッションを開始する（コア）

1. 利用者がエラーメッセージ / スタックトレース / ログを貼り付ける
2. 任意で、関連するコード断片・言語 / FW・「直前にした変更」を添える
3. システムは内部で原因を診断する（**利用者には一切見せない**）
4. **Gate A**: 着眼点のヒントのみを提示する（設問はまだ出ない）

#### UC-02 ヒントだけで自力解決する（最良の結末）

1. 利用者は Gate A のヒントを見て、自分で調べて解決する
2. 「解決した」を押し、原因を自分の言葉で記述する
3. 到達判定を受け、**自力解決**として記録される

#### UC-03 設問に答えて段階を進める（Gate B）

1. Gate A で進まない場合（一定時間経過 or 利用者が「設問に進む」を押す）、Gate B に入る
2. Lv1（観察）から順に、選択式の設問が 1 問ずつ提示される
3. 正誤に応じて、**答えを漏らさない**フィードバックが返る
4. 段階が上がる（Lv1 → Lv5）

#### UC-04 原因を宣言してセッションを完了する

1. 利用者が「原因が分かった」を押し、自分の言葉で原因を記述する
2. システムが内部診断と突き合わせて到達判定を行う
3. 到達していれば完了、していなければ差分を踏まえた設問に戻る

#### UC-05 答えの開示を受ける（Gate C）

1. Gate B を通しても到達できない場合、開示が解放される
2. 原因・根拠・修正方針・再発防止策が提示される
3. **開示後も振り返りは必ず実施する。** 「どこで見落としたか」を言語化させる

#### UC-06 振り返りレポートを見る

1. セッション完了時、以下が生成される
   - デバッグ脳スコア（5 軸）と到達ゲート
   - どの段階でつまずいたか
   - **一般化された学び**（次に転用できる形）
2. レポートは履歴として保存される

#### UC-07 自分の成長を見る（個人ダッシュボード）

1. 到達ゲートの分布、5 軸スコアの推移、学習時間、正答率を見る
2. **自分のデータは常に自分が見られる**（P6 の前提）

### 4.2 演習モード（利用者 + 運用者）

#### UC-08 割り当てられた問題を解く

1. 運用者から問題（または問題セット）が割り当てられ、通知される
2. 利用者は実務モードと同じ 3 ゲートの体験で解く
3. 結果は**同一条件で他メンバーと比較可能**な形で記録される

#### UC-09 問題を割り当てる（運用者）

1. 運用者が社内問題集から問題セットを選ぶ
2. 対象メンバー（個人 / チーム全員 / 新入社員グループ）と期限を指定する
3. 進捗と結果を一覧で追える

#### UC-10 実務セッションを問題集に登録する（運用者）

1. 完了した実務セッションのうち、教材価値の高いものを選ぶ
2. **匿名化・汎用化**（社名・パス・固有名詞の除去）を行い、問題集に登録する
3. 難易度・カテゴリ・対象レベルのタグを付ける

### 4.3 組織（管理者・閲覧者）

#### UC-11 組織ダッシュボードを見る

1. 管理者がメンバー横断の状況を見る
   - 取り組み時間・セッション数
   - 到達ゲートの分布（自力解決率）
   - 正答率、正解までの平均所要時間
   - 5 軸のチーム平均と個人分布
2. 弱い軸が組織全体の傾向として見える（例:「検証力が全体的に低い」）

#### UC-12 ランキングを見る

1. 演習モードの共通問題について、順位を表示する
2. **既定は「チーム内・任意参加・期間限定」**。全社常時ランキングは管理者が明示的に有効化した場合のみ

#### UC-13 評価レポートを出力する（人事評価用）

1. 管理者が対象メンバーと期間を指定する
2. 5 軸スコア、成長率、到達ゲート分布、取り組み量を含む**説明可能なレポート**を出力する
3. **単一の総合点だけを出す形にはしない。** 根拠となる内訳を必ず併記する

## 5. 機能要件

### 5.1 問答エンジン（コア）

| ID | 機能 | 要件 | 優先度 |
|---|---|---|---|
| FR-01 | エラー投稿 | エラーテキスト（必須, 最大 20,000 文字）、コード断片、言語 / FW、直前の変更を受け付ける | Must |
| FR-02 | 内部診断 | LLM が原因仮説・根拠・確信度を生成し、**サーバ内部にのみ**保持する | Must |
| FR-03 | **Gate A: ヒント提示** | 設問を出さず、着眼点のヒントのみを段階的（Lv1〜3）に提示する | Must |
| FR-04 | **Gate B: 段階的出題** | Lv1〜Lv5 の各段階について、選択式（2〜5 択）の設問を 1 問ずつ生成・提示する | Must |
| FR-05 | 回答判定 | 選択に対して正誤を判定し、答えを漏らさないソクラテス式フィードバックを返す | Must |
| FR-06 | 段階遷移 | 正解で次段階へ。不正解時は同段階内で角度を変えた再出題（同段階最大 3 問） | Must |
| FR-07 | **ゲート遷移条件** | A→B は「一定時間経過」または「利用者の要求」。B→C は「全段階通過後も未到達」または「詰まり条件」 | Must |
| FR-08 | 漏洩ガード | Gate A・B の生成文に原因の直接開示・修正コードが含まれていないか検査し、含む場合は再生成する | Must |
| FR-09 | 原因宣言と到達判定 | 利用者の自由記述を内部診断と照合し、到達 / 部分到達 / 未到達を判定する | Must |
| FR-10 | **Gate C: 開示** | 原因・根拠・修正方針・再発防止策を提示する。開示後も振り返りは必須 | Must |
| FR-11 | 秘匿情報マスキング | 入力から API キー / トークン / パスワード / 絶対パス等を検出し、保存・送信前にマスクする | Must |
| FR-12 | モデル選択 | 用途別（診断 / 出題 / 判定）に OrcaRouter のモデルを設定で切り替えられる | Should |
| FR-13 | 先行診断 | 内部診断をセッション作成レスポンスから分離し、利用者が Gate A を読んでいる間に別リクエストで完了させる | Must |
| FR-14 | 冪等な状態変更 | 回答・診断・原因宣言の各リクエストは、二重送信されても結果が変わらない | Must |
| FR-15 | 診断失敗時の継続 | 内部診断が失敗しても、汎用モードで問答を継続できる | Should |

### 5.2 計測と評価

| ID | 機能 | 要件 | 優先度 |
|---|---|---|---|
| FR-20 | 到達ゲート記録 | どのゲートで解決したか（A / B / C / 未解決）を記録する | Must |
| FR-21 | 5 軸スコアリング | 観察 / 切り分け / 仮説 / 検証 / 修正を 0〜100 で算出する | Must |
| FR-22 | 計測項目の記録 | 所要時間、正答率、ヒント使用回数、設問数、段階別所要時間を記録する | Must |
| FR-23 | 振り返りレポート | つまずき箇所・一般化された学び・次回の着眼点を生成する | Must |
| FR-24 | 個人ダッシュボード | 自分の到達ゲート分布・5 軸推移・学習時間・正答率を表示する | Must |
| FR-25 | **難易度正規化** | 演習問題に難易度を持たせ、スコアを難易度で正規化する | Must |
| FR-26 | **成長率の算出** | 直近と過去の比較により、絶対値ではなく伸びを算出する | Must |
| FR-27 | 評価レポート出力 | 期間・対象を指定し、5 軸 / 成長率 / 到達ゲート分布 / 取り組み量を含むレポートを出力する（PDF or CSV） | Should |

### 5.3 組織・演習・問題集（BtoB）

| ID | 機能 | 要件 | 優先度 |
|---|---|---|---|
| FR-30 | 組織テナント | 組織を単位としたデータ分離。組織をまたいだ参照は不可 | Must |
| FR-31 | 認証 | メンバーはログインして利用する。SSO（OIDC）または GitHub OAuth | Must |
| FR-32 | ロール管理 | `member` / `lead` / `admin` の 3 ロール。閲覧できる範囲を制御する | Must |
| FR-33 | メンバー管理 | 招待・無効化・チーム（グループ）への所属設定 | Must |
| FR-34 | 社内問題集 | 問題の登録・編集・タグ付け（難易度 / カテゴリ / 対象レベル） | Must |
| FR-35 | **実務→問題集の変換** | 完了した実務セッションを、匿名化・汎用化して問題集に登録する | Should |
| FR-36 | 問題の割り当て | 対象（個人 / チーム）と期限を指定して問題セットを配布する | Must |
| FR-37 | 割り当て進捗管理 | 未着手 / 進行中 / 完了の一覧と督促 | Should |
| FR-38 | 組織ダッシュボード | メンバー横断の取り組み時間・自力解決率・正答率・所要時間・5 軸分布 | Must |
| FR-39 | ランキング | 演習モードの共通問題について順位を表示する。**表示範囲と有効/無効は組織設定で制御** | Should |
| FR-40 | 組織設定 | ランキングの可否、評価レポートの利用可否、データ保持期間の設定 | Must |

### 5.4 スコープ外（v1 では作らない）

| 項目 | 理由 / 予定 |
|---|---|
| レスポンスのストリーミング表示 | enebular クラウド実行環境では原理的に不可（[E1](architecture.md#2-enebular-採用にともなう-4-つの制約)）。FR-13 の先行診断で代替する |
| 人事システムへの自動連携 | レポート出力までが本製品の責務（Non-Goals）。API 提供は v2 で検討 |
| スクリーンショット OCR 入力 | テキスト貼り付けで価値検証は可能。v2 |
| IDE 拡張 / CLI | 体験の入口を増やす施策。コア価値の確定後。v3 |
| 多言語 UI（英語） | v1 は日本語のみ。v2 |
| 課金 / プラン管理 | v1 は導入企業と個別契約。v2 |
| デバッグ以外の領域（設計 / レビュー / テスト設計） | 3 ゲート方式は他領域にも展開しうるが、まずデバッグで確立する。v3 |

## 6. 非機能要件

### 6.1 パフォーマンス

レスポンスはバッファされるため（[E1](architecture.md#2-enebular-採用にともなう-4-つの制約)）、
「1 文字目まで」ではなく**レスポンス全体の完了時間**で規定する。

| ID | 要件 |
|---|---|
| NFR-P1 | エラー投稿から **Gate A のヒントが表示されるまで 5 秒以内**。内部診断はこの経路に含めない（FR-13） |
| NFR-P2 | 回答送信から次の設問が表示されるまで **4 秒以内** |
| NFR-P3 | セッション完了からレポート表示まで **10 秒以内**（初回生成時） |
| NFR-P4 | 組織ダッシュボードの表示は **3 秒以内**。集計はセッション完了時に事前計算する |
| NFR-P5 | すべてのリクエストは実行環境のタイムアウト内に収める。1 リクエストで LLM を 2 回以上直列に呼ばない |

### 6.2 セキュリティ / プライバシー

BtoB では、**業務コードとエラーログという機微な資産**を預かる。要求水準が上がる。

| ID | 要件 |
|---|---|
| NFR-S1 | OrcaRouter の API キーはクラウド実行環境の環境変数にのみ保持し、FE とリポジトリに露出させない |
| NFR-S2 | 利用者入力は**認証情報が混入する前提**で扱う。保存前・LLM 送信前に自動マスキング（FR-11） |
| NFR-S3 | 内部診断と各設問の正解は Gate C 到達前の API レスポンスに含めない。データストア上も別テーブルに隔離する |
| NFR-S4 | 入力データを LLM プロバイダの学習に使わせない設定を OrcaRouter 側で確認・明記する |
| NFR-S5 | **テナント分離**: すべてのデータアクセスに組織 ID を含め、他組織のデータを参照できないことをリポジトリ層で強制する |
| NFR-S6 | **ロールに応じた閲覧制御**: `member` は自分のデータのみ。`lead` は自チーム。`admin` は組織全体 |
| NFR-S7 | データ削除に対応する（個人セッション / 退職者データ / 組織全体） |
| NFR-S8 | フロントと API は別オリジンのため、CORS は `ALLOWED_ORIGIN` の完全一致で許可する |
| NFR-S9 | **監査ログ**: 誰が誰の評価データを閲覧したかを記録する（P6 の担保） |

### 6.3 公平性・説明可能性 ★評価に使うため必須

| ID | 要件 |
|---|---|
| NFR-F1 | **スコアの算出根拠を利用者本人が確認できる。** ブラックボックスな数値を人事評価に使わない |
| NFR-F2 | 横比較に使ってよいのは**演習モード（同一問題）のみ**。実務モードのスコアで順位付けしない |
| NFR-F3 | 難易度による正規化を行う（FR-25）。難しい問題に挑んだ人が不利にならない |
| NFR-F4 | **Gate C（開示）の利用を減点の主因にしない。** 詰まったときに開示を避ける動機を作らない |
| NFR-F5 | 評価レポートは単一の総合点だけを出さず、必ず内訳と根拠を併記する |
| NFR-F6 | 利用者は自分のデータを常に閲覧でき、事実誤認があれば異議を申し立てられる導線を持つ |

> **根拠**: 指標が評価に使われた瞬間、指標は歪む（Goodhart の法則）。
> 対策を設計に埋め込まないと、「簡単なエラーだけ投げる」「詰まっても開示を使わず放置する」
> といった行動を誘発し、**業務支援としての価値まで壊れる**。
> 詳細は [evaluation-model.md](evaluation-model.md)。

### 6.4 コスト・リソース

| ID | 要件 |
|---|---|
| NFR-C1 | 1 セッションあたりの LLM 総トークン数に上限を設ける（既定: 入出力合計 80k tokens） |
| NFR-C2 | 用途別にモデルを使い分ける。診断は高性能、出題・判定は安価な高速モデル |
| NFR-C3 | 内部診断結果はセッション内でキャッシュし、質問生成のたびに再診断しない |
| NFR-C4 | **データストアのアクセス回数を 1 ターン 4 回以内**に保つ。1 セッションは少数アイテムに集約する |
| NFR-C5 | LLM 待ち時間は実行環境の実行時間として計上されるため、1 リクエストの LLM 呼び出しは原則 1 回 |
| NFR-C6 | **ダッシュボードの集計はセッション完了時に事前計算し、閲覧時に全件走査しない**（KV ストアに集計クエリがないため） |

### 6.5 可用性・運用

| ID | 要件 |
|---|---|
| NFR-O1 | LLM 呼び出し失敗時は OrcaRouter のフォールバックモデルへ自動切り替えする |
| NFR-O2 | 全 LLM 呼び出しについて、用途 / モデル / トークン数 / レイテンシ / `X-Orca-*` を構造化ログに残す |
| NFR-O3 | レート制限（既定: 10 セッション / 時 / メンバー）を設ける |
| NFR-O4 | 内部診断が失敗しても、汎用モードで問答を継続できる |
| NFR-O5 | development / production を分離し、本番デプロイは GitHub Actions からのみ行う |

### 6.6 品質

| ID | 要件 |
|---|---|
| NFR-Q1 | 漏洩ガード（FR-08）の検出漏れ率を、代表 50 ケースの回帰テストで 0 件に保つ |
| NFR-Q2 | ドメインロジック（ゲート遷移・段階遷移・スコアリング・正規化）は LLM にもデータストアにも依存しない純関数として実装する |
| NFR-Q3 | ローカル環境で、Lambda を介さずに同じルーターを HTTP サーバとして起動できる |
| NFR-Q4 | **スコア算出は再現可能。** 同じセッションデータからは常に同じスコアが出る（LLM を介在させない） |

## 7. 成功指標（KPI）

BtoB のため、**利用者の指標**と**組織の指標**を分けて置く。

### 7.1 利用者側（これが崩れると何も溜まらない）

| 指標 | 定義 | v1 目標 |
|---|---|---|
| **継続利用率** | 導入企業のメンバーのうち、月 1 回以上使った割合 | 60% |
| セッション完走率 | 開始したセッションのうち完了したもの | 60% |
| **自力解決率** | Gate A または B で解決したセッションの割合 | 55% |
| Gate A 解決率 | ヒントのみで解決した割合 | 20% |

### 7.2 組織側（これが導入の理由）

| 指標 | 定義 | v1 目標 |
|---|---|---|
| **スコア成長** | 3 セッション以上実施したメンバーの初回→最新の 5 軸平均の差 | +10 pt |
| 演習カバレッジ | 割り当てた問題のうち期限内に完了した割合 | 80% |
| 問題集の内製率 | 社内の実務セッションから生成された問題の割合 | 30% |
| **評価利用率** | 評価面談で本レポートを参照した管理者の割合 | 50% |

> **最重要は自力解決率。** これが低ければ Gate A のヒント設計かゲート遷移条件が弱い。
> 逆に 90% を超える場合は簡単すぎ、学習効果も評価の分解能も薄い。

## 8. 前提と制約

| # | 内容 |
|---|---|
| A-1 | LLM へのアクセスは **OrcaRouter 経由に限定**する（必須要件） |
| A-2 | バックエンドは **enebular クラウド実行環境（ZIP / Node.js）**、永続化は **enebular データストア**に限定する（必須要件） |
| A-3 | デプロイは **GitHub Actions + `@uhuru/enebular-cli`** で自動化する（必須要件） |
| A-4 | **提供形態は BtoB。** 組織単位で契約し、メンバーは認証して利用する |
| A-5 | v1 の UI 言語は日本語のみ |
| A-6 | 本製品は評価**レポートを出力する**ところまでを責務とし、人事システムへの自動連携は行わない |
| A-7 | データストアのテーブル数上限（フリー 10 / エンタープライズ 100）に収まる設計とする。BtoB 提供のため**エンタープライズプラン前提**とする |
