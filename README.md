# SocraMetry

> **答えを教えない AI メンター。** エラーを投げると、返ってくるのは解決策ではなく「気づきを促す質問」。

## これは何か

**SocraMetry**（Socratic + Metry = ソクラテス式問答 × 計測）は、
**デバッグ能力そのものを鍛える**ための学習サービスです。

エラー画面やログを貼り付けると、AI は答えを言いません。代わりに、熟練の先輩エンジニアのように
**段階的な選択式の質問**を投げかけてきます。

```
🧑 「TypeError: Cannot read properties of undefined (reading 'map')」って出ました

🤖 なるほど、そのエラーですね。まず確認させてください。
   このメッセージは「何が undefined だった」と言っていますか？

   A. map という名前の変数
   B. map を呼び出そうとした対象のオブジェクト
   C. map の引数に渡した関数
   D. map の戻り値

🧑 → B

🤖 その通りです。では、そのオブジェクトはどこから来ていますか？
   直前に何を変更しましたか？
   ...
```

ユーザーは質問に答えながら、**自分の脳で**原因にたどり着きます。
そして「自力で解決した」という快感を得ます。

## なぜ作るのか

生成 AI がコードを書いてくれる時代になり、開発速度は上がりました。
しかしその副作用として、**「動いたけれど、なぜ動いたか分からない」「エラーを AI に投げて直してもらったが、次も同じ場所で詰まる」**
という状態のエンジニアが増えています。技術力が定着しないのです。

AI がやっているのは *答えの提示* であり、*思考の訓練* ではないからです。

SocraMetry は、その AI の使い方を反転させます。
**AI に問題を解かせるのではなく、AI に問題を出させる。**

## デバッグの「型」を鍛える

SocraMetry は、熟練者が無意識に行っているデバッグのプロセスを 5 段階に分解し、
各段階を質問によって訓練し、**計測（Metry）** します。

| Lv | 段階 | 鍛える力 | 質問の例 |
|----|------|----------|----------|
| 1 | **観察** Observe | エラーを正確に読む | 「このメッセージは何が undefined だと言っていますか？」 |
| 2 | **切り分け** Localize | 問題箇所を絞る | 「エラーが出る直前に、どの設定ファイルを変更しましたか？」 |
| 3 | **仮説** Hypothesize | 原因を推論する | 「ログ 3 行目のパラメータは、期待通りの型になっていますか？」 |
| 4 | **検証** Verify | 仮説を確かめる | 「その仮説が正しいと確認するには、まず何を出力しますか？」 |
| 5 | **修正** Fix | 再発しない直し方 | 「同じミスを二度と起こさないために、どこに何を足しますか？」 |

セッション終了後、5 軸のレーダーチャートで **デバッグ脳スコア** が可視化され、
セッションを重ねるごとに自分の弱点（例:「観察は強いが検証が弱い」）が見えてきます。

## 技術スタック

| レイヤ | 採用 |
|---|---|
| フロントエンド | Next.js 15 (App Router) / TypeScript / Tailwind CSS |
| バックエンド | Hono (Node.js 22+) / TypeScript |
| LLM ゲートウェイ | **OrcaRouter**（必須・OpenAI 互換） |
| データベース | PostgreSQL / Prisma |
| モノレポ | pnpm workspaces + Turborepo |

> LLM へのアクセスは**すべて OrcaRouter 経由**に統一します。API キーはバックエンドにのみ保持し、
> フロントエンドから LLM を直接叩くことはありません。詳細は [architecture.md](docs/architecture.md) 参照。
